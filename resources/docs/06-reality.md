# 06 · REALITY 上线

**读之前**：不确定 REALITY、dest、SNI、指纹是什么的话，
先过一遍 [00 · 术语表](00-glossary.md) 的第三节。

---

## 0. 它解决什么，代价是什么

**问题**：一台自建代理服务器，证书是自签的、或者域名是新注册的没什么流量。
主动探测一下——直接连它的端口，看它返回什么——就露馅了。

**REALITY 的做法**：借用一个真实网站的握手。带着正确密钥来的是自己人，
转给代理；没有密钥的探测者，会被**原样转发给那个真网站**，
看到的是那个网站真实的证书和响应。从外面看，这台机器"是"那个网站。

**代价**：

| 代价 | 说明 |
|---|---|
| 只能 vless + tcp | 用不了 ws/grpc 这些传输 |
| 要选一个 dest 并长期依赖它 | dest 挂了，节点就**静默失效**（端口还在听，但没人能握手） |
| 密钥轮换会断所有老客户端 | 直到他们更新订阅 |
| 选 dest 要花心思 | 选错了伪装就是假的，见下一节 |

**什么时候不需要**：线路没有被主动探测的压力时，
`vmess + tcp` 简单可靠，先跑通再说。

---

## 1. 选 dest## 1. 选 dest —— 这一步决定成败

dest 是被借用的那个站。选错的话 REALITY 提供的伪装就是假的。

### 硬判三关

| 关 | 为什么 |
|---|---|
| TLS 1.3 | REALITY 只能借 TLS 1.3 的握手 |
| **握手时延 ≤ 150ms** | `[D]` **dest 的握手时延加在每一条用户连接上** —— REALITY 服务端每条连接都要新建一个到 dest 的连接并让它全程参与握手。实测换一个慢 293ms 的 dest，客户端每个新连接就多花 303ms（`compatibility/dest-latency.md`） |
| **X25519 可协商** | 客户端普遍只提供 X25519；dest 只认 P-256 之类的话握不上 |
| HTTP/2 | 现代站点的常态，没有 h2 反而显眼 |
| 非 CDN | CDN 的 SNI↔IP 映射不稳定，且同一 IP 后面什么都有，反而可疑 |

### 用扫描器

`[!!]` **必须在目标节点上跑**：可达性与延迟是"这台机器到那个站"的关系，
而 REALITY 握手时是落地去连 dest。在开发机上跑只能验工具本身。

```bash
bash lab/scan-real.sh --build                 # 编出静态二进制
scp dist/destscan-linux-amd64 <节点>:/tmp/destscan
ssh <节点> '/tmp/destscan www.a.example www.b.example ...'
```

输出会给每个候选一个判定（`pass` / `no_tls13` / `no_x25519` / `cdn` / `no_h2` /
`slow` / `error`）与延迟。

`[!]` 四关全过只是**及格线**。选谁还要看：够不够冷门（用烂的站本身就是特征）、
以及这个 SNI 出现在**客户端实际连的那一跳**的 IP 上自不自然 ——
有中转时那一跳是中转，工具判不了这个。

`[!!]` 还要看它**承不承受得住**。`[S]+[D]`（`compatibility/dest-latency.md` 附）：
每条用户新连接各触发**一次到 dest 的建连**，**严格 1:1，且全部来自落地那一个
IP**；一个配错了的客户端因为重试，压力是正常客户端的 **5 倍**。

所以别选小站/小镜像站 —— 它可能限流或封 IP，而表现是"部分用户偶发连不上"。

`[!]` 不必恐慌：长连接**只付一次**握手成本（同一连接上 10 个请求 → dest 只有
1 条连接），所以正常使用下的连接速率远低于"并发用户数"给人的直觉。

`[!!]` 别用 `www.samsung.com`、`www.apple.com` 这类 —— 它们是 REALITY 教程里的
默认值，用的人太多，本身就成了特征。

面板也集成了扫描，`[D]` 实测走通：

1. 节点编辑页 → 「dest 候选清单」填域名，一行一个 → 勾上「重新筛查」→ 保存
2. 面板下发一个 `scan_id`，节点在下一个拉取周期取走
3. 节点跑完一轮（几十秒）后回报，**结果就显示在同一个编辑页上**

结果表里合格与不合格的**都会列出来**（不合格的标出是哪一关没过），
因为"为什么这个不能用"和"哪个能用"同样重要。

`[!]` 改了候选清单会换一个新的 `scan_id`，旧的那轮结果不会覆盖新任务 ——
运维改完清单立刻看到的是"还没回报"，而不是上一轮的旧数据。

## 2. 在面板上开启

节点编辑页：

| 字段 | 说明 |
|---|---|
| 协议 | `vless` |
| 流控 | `xtls-rprx-vision` |
| 启用 REALITY | 勾上 |
| dest | `mirrors.example.com:443` |
| server_names | 通常就是 dest 的域名 |
| 重新生成密钥 | `[!]` 勾上会换密钥对，**所有老客户端立刻连不上**，直到订阅更新 |

私钥由面板生成并保存，**只下发给节点、绝不进订阅**。订阅里只有公开子集
（public-key / short-id / servername / flow）。

## 3. 节点侧

不需要改 `agent.conf` —— REALITY 的权威通道是 nodeInfo 的 `custom_config`
（见 [07](07-api-node.md)）。节点拉到新配置后会发现监听形态变了，重启内核。

日志里会看到：

```
node listen config changed, restarting core  from=... to=...
core started  port=39500 protocol=vless transport=tcp security=reality
```

`[!]` 日志里的 REALITY 私钥是**哈希后**的指纹，不是明文。

## 4. 验证

**面板侧**：节点列表的状态列会显示 dest 健康。
`dest 不可达` 是个单独的标记 —— 因为：

`[!!]` dest 挂掉是**静默的**：端口照常监听、节点照常显示"在线"、
`/health` 照常 200，而没有任何客户端能完成握手。

**节点侧**：

```bash
curl -s 127.0.0.1:9090/ready     # dest 连续失败到阈值时会失败
curl -s 127.0.0.1:9090/metrics | grep reality_dest
```

**客户端侧**：拿订阅导入 Mihomo/v2rayN 连一次。

`[!!]` 连不上时**先看节点日志，不是客户端日志**。实测（故意把客户端的 flow 留空）：

| 哪一侧 | 说了什么 |
|---|---|
| 客户端（info 级） | 只有一行 `match ... using <节点名>` —— **没有任何拒绝原因** |
| 节点（`journalctl -u agent`） | `account xxx is rejected since the client flow is empty` —— 说得清清楚楚 |

原因很直白：拒绝发生在**服务端**，客户端只知道连接断了。
所以排 REALITY 连不上的问题，顺序是：

```bash
# 在节点上
journalctl -u agent --since "-5min" --no-pager | grep -iE "reject|invalid|flow"
```

`[!]` 客户端日志仍然值得调到 `info`（很多客户端默认 `warning`），
但它回答的是"有没有走到这个节点"，不是"为什么被拒"。

## 5. 常见失败

| 现象 | 多半是 |
|---|---|
| 客户端握手超时 | dest 不可达，或节点端口被防火墙挡 |
| `TLS: internal error` | 公钥/short-id 与节点不匹配（订阅没更新？刚重新生成过密钥？） |
| 连上但立刻断 | 客户端开了 Mux/smux —— `[!!]` 对接 xray 内核的节点**一律不要开** |
| 连不上，客户端日志什么理由都没有 | `[D]` 正常 —— 理由在**节点**日志里。见上面 §4 的排查顺序 |
| 节点日志 `client flow is empty` | 客户端没配 `flow: xtls-rprx-vision`。两端必须一致 |
