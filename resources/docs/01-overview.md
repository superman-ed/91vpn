# 01 · 系统总览 —— 整套东西由哪几块拼成

> **读法**:零假设。先讲"整套系统有哪几块、各干什么、怎么串起来",再看架构细节。
> 读之前最好先过 [00 · 术语表](00-glossary.md) 的「零、一分钟看懂整件事」。纯文字。

---

## 一句话

一套**机场/代理服务**:用户在客户端连我们的节点上网,面板管用户和节点。
技术上分三大块——**客户端**(用户设备上)、**面板**(我们的管理网站)、**节点**(我们的一台台服务器)。

---

## 整套系统由哪几块(大白话)

| 块 | 是什么 | 跑在哪 |
|---|---|---|
| **客户端** | 用户装的 App,内置 **Mihomo 内核**负责真正连接;安卓 + Windows | 用户设备 |
| **面板(Laravel)** | 我们的管理网站:用户/套餐/订单/**订阅**、**节点管理/转发规则** | 我们的服务器 |
| **Agent(Go)** | 跑在**每台节点**上的小程序:从面板拉配置和用户名单、管代理内核、上报流量 | 节点机 |
| **Xray 内核** | Agent 内部**作为库嵌入**的代理内核,真正收发流量的那层 | 节点机(在 Agent 进程里) |
| **节点** | 一台服务器,分**落地/中转**两种角色(见下) | 我们的服务器 |

> `[!]` 客户端用 **Mihomo** 内核,节点用 **Xray** 内核——两边内核不同,靠协议(vmess/vless)对接,不需要一样。

---

## 它们怎么串起来(整体流程)

```
【用户设备】客户端 App(Mihomo 内核)
     │  ① 拉订阅(得到"有哪些节点、怎么连")     ┌───────────────────────┐
     ├──────────────────────────────────────────▶│  面板 (Laravel)        │
     │                                            │  用户/套餐/订单/订阅    │
     │  ② 选一个节点连上                           │  节点管理/转发规则      │
     ▼                                            └───────────┬───────────┘
【节点】Agent(Go)+ Xray 内核  ◀──拉配置/用户名单·上报流量──── mod_mu(HTTP)
     │  ③ 你的流量从这里出去
     ▼
   目标网站
```

- **① 订阅**:客户端拿一条 URL 定期去面板拉"当前节点清单+连法"(节点增减/换密钥自动同步)。
- **② 连接**:客户端选一个节点,按订阅里的参数连上去。
- **③ 出口**:流量经节点的 Xray 内核出去访问网站。
- **mod_mu**:节点的 Agent 和面板之间的接口——Agent 靠它拉配置/用户名单、上报流量(见 [07](07-api-node.md))。它是 **sspanel-uim 的契约**,所以我们的 Agent 也能对接任何实现了该契约的面板,不限本项目。

---

## 两种节点角色(整个中转架构的地基)

| 角色 | 认证用户 | 持有用户名单 | 端口来自 | 进用户订阅 |
|---|---|---|---|---|
| **落地**(landing) | 是 | 是 | 节点自身配置 | 是 |
| **中转**(relay / springboard / front) | **否** | **否** | 转发规则 | 否(订阅发的是它的**入口地址**) |

**大白话**:落地真正替用户出去上网、认证并计流量;中转夹在中间做加速的"二传手",只搬字节。

`[!!]` **D-1:中转不认证用户,因此绝不接收用户名单与凭据。** 这是硬边界不是优化——中转机常是租来、最易被接管的那台,而一份用户名单+凭据就是整个服务的钥匙。面板在读写两个方向都有守卫,详见 [05](05-relay.md)。

---

## 部署形态(我们实际怎么摆的)

- **面板对外分两个域名**(同一个应用,两个入口):
  - **用户面** `app.91app.shop`:公开,用户/客户端访问(订阅、客户端 API)。
  - **后台** `summer.91app.shop`:管理员专用,**Cloudflare Access 身份门 + 只经隧道**,公网访问 `/admin` 直接 404。
- **源站不对公网开端口**:一切经 Cloudflare Tunnel 进来,藏源站 IP。
- 节点上只跑 Agent(一条命令一键部署,见 [04](04-node-deploy.md))。

> 为什么分两个域名:后台有"SSH 到全网节点"这类高危操作,不能和用户面共处一个敞开的入口。详见 [03](03-panel-deploy.md)。

## Agent 和 soga 是什么关系

我们的 Agent 是 **soga 的独立重写**,不是它的分支或改版:

```
目标 soga(闭源二进制) ──逆向──▶ 行为规格 ──重新设计──▶ 独立实现(Go) ──对照──▶ 兼容性测试
```

`[D]` 已验证:真 soga 和本 Agent 打同一个面板时,**端点集合与调用比例一致**(见 [10](10-compat-soga.md))。差别是我们的实现**可审计、可控**,而 soga 闭源。

---

## 相比 soga,我们好在哪(为什么值得自研)

| 方面 | 说明 |
|---|---|
| 状态同步 | 只下发**变更**,不是每次全量重建 |
| 上报可靠性 | 失败进**持久化队列**,面板恢复后补报,不丢账 |
| 计量口径 | 按**线路字节**计量,和机房账单口径一致 |
| 校验 | 配置非法**启动即失败**,不静默降级 |
| 可观测 | `/health` `/ready` `/metrics` 三个端点(见 [09](09-ops.md)) |
| 中转 | 转发规则、健康检查、PROXY protocol 配对校验(见 [05](05-relay.md)) |
| 内核 | **嵌入 Xray 作库**、不 fork 子进程:配置变更不重启进程、内核崩溃不留孤儿进程 |
