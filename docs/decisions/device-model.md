# D-6 —— 设备模型：一台设备一个凭据

状态：**阶段一已上线（`e379f3a`）· 阶段二待定**（2026-09-23）
起因：L-08 —— 「在线设备数」量的其实是 IP 数

---

## 1. 问题

`[D]` 现状：设备上限靠 `alive_ips` 的 `(user_id, ip)` 去重来数，而它**两个方向都错**：

```
家里三台设备共用宽带出口   → 只算 1 台（少算，等于放过共享）
一台手机 Wi-Fi 切蜂窝      → 算 2 台（多算，等于误伤正常用户）
```

`[D]` 实测的套餐上限：轻量 3 · VIP① 4 · VIP② 7 · VIP③ 9 · 定制 36/60。
**轻量套餐用户开三台设备正好占满，一出门切网就超限。**

`[D]` 2026-09-23 已修掉「踢错人」那一半（`blockedIps()` 改按 `last_seen` 倒序），
但那只是把伤害从「踢掉你正在用的」降到「踢掉你确实不在用的」。**根本问题没动。**

---

## 2. 为什么协议层只有一条路

`[S]` VLESS / VMess 的连接只携带 **UUID（标识用户）+ 源 IP**，**没有任何设备标识**。

`[!]` 即便客户端是自研的也一样（本项目 Android / Windows 已自研，iOS / macOS 后续跟上）：
自研客户端能通过**另一条 API 通道**上报设备 ID，但 **xray 看不见那条通道** ——
它只认握手里的 UUID。所以"限几台设备"只能落在"一个用户名下有几个 UUID"上。
详见 §3.6。

`[!]` 考虑过并排除的：

| 方案 | 为什么不行 |
|---|---|
| 客户端上报设备号 | 自研客户端能报，但 **xray 看不见那条通道**，管不住实际连接；且 iOS/macOS 在自研版上线前只能用标准客户端 |
| TLS 指纹 / 连接特征 | 不可靠；而且 REALITY 刻意把指纹归一化（`client-fingerprint: chrome`） |
| 继续按 IP 数，调参数 | 参数怎么调都改不了"IP ≠ 设备" |

`[!!]` **2026-09-23 更正：本节原本写的是"剩下唯一可行的：一台设备一个凭据"。
那句话太满了** —— 实际上线的 `e379f3a` 走了另一条：**应用层按 `device_id` 统计**。
两者不是对错关系，是同一根轴上的两个位置（见 §2b）。

**协议层唯一可行的仍是：一台设备一个凭据 —— 凭据本身就是设备。**
但"协议层"不等于"唯一值得做的"。

## 2b. 两个阶段（`[D]` 阶段一已上线）

| | 执行点 | 覆盖 | 能否绕过 | 状态 |
|---|---|---|---|---|
| **阶段一** | 订阅下发 / 设备上报时 | 携带 `device_id` 的自研客户端 | **能** —— 把订阅导进第三方客户端即绕过 | `e379f3a` 已上线 |
| **阶段二** | 凭据本身（本文 §3） | 所有客户端 | 不能 | 待定 |

### 阶段一做了什么（`e379f3a`）

`[S]` `DeviceService::admit()`：已知设备刷新放行；未满额登记新设备；
满额时回收一台**超过 15 天未上报**的陈旧设备，没有可回收的才抛 `DeviceLimitException`。
`SubController` 在 `/sub/{token}?device_id=` 带 id 时准入、超限 403；
**不带 id 时跳过**（兼容第三方客户端与旧版官方端）。上限取 `users.node_ip_limit`（0 = 不限）。

`[!]` 它解决了数 IP 的两个毛病：**多设备共出口 IP 各自算清、单设备换 IP 仍算一台**。
`[!!]` 它**没有**解决绕过：不带 `device_id` 的请求直接跳过检查。
那部分仍由节点侧的在线 IP 计数兜底（即 L-08 的旧机制，2026-09-23 已修掉"踢错人"）。

### 阶段二的触发条件（可观测，不是"以后再说"）

`[!!]` **不要凭感觉决定做不做阶段二。** 判据是：

```
绕过率 = 不带 device_id 的订阅拉取 ÷ 全部订阅拉取
```

绕过率高、且带宽成本确实被少数账号吃掉时，阶段二才有价值。
否则它是三到四天的工程换一个没发生的问题。

## 2c. `[!]` 绕过率现在【测不了】—— 要先加一列

`[D]` `subscribe_logs` 现有列：`user_id / type / ip / location / client / fetched_at`。
**没有记录 `device_id` 带没带**，所以上面那个分母有、分子没有。

`[!]` 用 `client`（User-Agent）近似替代**不可靠**：UA 可伪造，而且旧版官方客户端
也不带 `device_id` —— 那是"没接线"，不是"绕过"，两者混在一起就得不出结论。

**要补的（一次迁移 + 一行）：**

```
① subscribe_logs 加 device_id varchar(64) NULL
② SubController::recordFetch 里写入 $request->query('device_id')
```

补完之后：

```sql
-- 绕过率（近 7 天）
SELECT
  COUNT(*)                                        AS 总拉取,
  SUM(device_id IS NULL)                          AS 不带id,
  ROUND(100 * SUM(device_id IS NULL) / COUNT(*), 1) AS 绕过率百分比
FROM subscribe_logs
WHERE fetched_at >= NOW() - INTERVAL 7 DAY;
```

`[!!]` **头几周这个数会很高且无意义** —— 自研客户端还没发布，iOS/macOS 也还没有，
所有人都在用第三方客户端。**等官方客户端上线并铺开之后再看这个数**，
否则会得出"绕过率 100%，必须做阶段二"这种假结论。

`[!]` 配合看的第二个数：**那些不带 `device_id` 的拉取，`user_id` 集中在少数人身上吗？**
分散 = 大家只是用惯了第三方客户端；集中在几个账号 = 那几个账号在共享。
后者才是阶段二要解决的，前者不是。

## 3. 阶段二的设计

### 3.1 表

```sql
user_devices
  id            bigint PK        -- 下发给节点的 id，流量按它回报
  user_id       bigint FK
  name          varchar(40)      -- 用户起的名字（"iPhone"、"家里电脑"）
  uuid          char(36) UNIQUE
  passwd        varchar(64)
  sub_token     char(32) UNIQUE  -- 每台设备一个订阅链接
  last_seen_at  timestamp NULL
  created_at / updated_at
```

`[!!]` **`id` 从 10,000,000 起自增**，与 `users.id` 刻意**不重叠**。
理由见 §3.2 —— 这不是洁癖，是让一种失败从"静默记错账"变成"明确拒收"。

### 3.2 节点下发与流量归属

```
下发   NodeUserService 每台【设备】一条：
         ['id' => device.id, 'uuid' => device.uuid, 'passwd' => device.passwd, …]
回报   节点把它收到的 id 原样报回来（[S] 现在就是这样，协议不用改）
归属   TrafficService 用 device.id 查 user_devices → 拿到 user_id → 累加到用户
```

`[!!]` **id 空间必须不重叠。** 半升级状态下，某个节点可能还缓存着旧的用户列表、
报回来的是 `users.id`。若两个空间重叠，那笔流量会被**静默记到另一个人头上**；
不重叠时它查不到设备、直接进"拒收"计数并告警 —— **失败要响，不要静默。**

`[!]` 用户级校验（`banned` / `class >= node_class`）位置不变，只是先经一次
device → user 的映射。

### 3.3 订阅

```
GET /sub/{token}
  ① 先查 user_devices.sub_token   → 用该设备的 uuid 生成
  ② 查不到再查 users.invite_token → 映射到该用户的【默认设备】（过渡期兼容）
```

`[!!]` ② 这条兼容是**迁移能做到零中断的关键**：老链接继续可用，老客户端继续能连。
上线后观察一段时间，确认没有流量再走 ② 时才删。

### 3.4 额度：从运行时惩罚改成配置时约束

```
现在   连接超限 → 踢人          永远会误伤，而且用户不知道为什么断
之后   添加设备超限 → 加不了     用户看到"你的套餐支持 4 台，已用 3 台"
```

`[!!]` 这是本设计**真正的收益**，比"数得准"更重要：
**把一个会误伤的运行时行为，换成一个说得清的配置时规则。**

`[!]` `plans` 新增 `device_limit`。**不复用 `ip_limit`** —— 两者语义不同，
复用会让"这个数字到底管什么"在迁移期无法解释。

### 3.5 `alive_ips` 怎么办

`[?]` **未决，需要你拍板。** 三个选项：

| | 做法 | 代价 |
|---|---|---|
| A | 保留上报、**不再踢人**，只作共享检测的信号 | 失去一个硬约束 |
| B | 改成**每设备**的 IP 上限（如 3） | 仍会误伤切网的用户，只是范围小了 |
| C | 整个移除 | 丢掉"一个凭据被 50 人共用"的唯一线索 |

`[i]` 我倾向 **A**：设备额度已经在配置时卡住了，运行时再踢一次是重复惩罚，
而它恰恰是误伤的来源。共享检测留着看，人工处理。

### 3.6 自研客户端怎么接

`[D]` 现状：Android / Windows 自研（未上线到 `client_downloads`），iOS / macOS 后续也会自研；
在此之前那两端只能用小火箭 / Clash 等标准客户端。

`[!!]` **四端全自研之后，执行点仍然是 per-device 凭据 —— 这一节不改变 §3 的设计。**
理由：真正把门的是代理服务端，而 **xray 只认握手里的 UUID**。
客户端上报的"设备 ID"走的是另一条 API 通道，xray 看不见它。
所以"限几台设备"只能落在"一个用户名下有几个 UUID"上。
**自研客户端改的是发放体验，不是执行模型。**

两条路径落在同一个模型上：

```
Android / Windows（自研）
  用户登录 → 客户端调 API 建设备 → 拿到自己的凭据 → 自动配好
  用户【完全不用】打开设备管理页

iOS / macOS（标准客户端，直到自研版上线）
  用户在面板加一台设备 → 扫那台的二维码 → 导入
  笨一点，但额度照样卡得住
```

`[!]` 这消掉了 D-6 的一个短板：per-device 凭据本来意味着用户要管理设备，
比现在"一个链接走天下"麻烦 —— **而在自研客户端里这个麻烦根本不出现。**

**要新增的 API：**

```
POST /api/user/devices/register
  入参  device_key（客户端本地生成并持久化的 ID）、name（机型）
  出参  该设备的 uuid / passwd / 订阅链接
```

`[!!]` **必须按 `device_key` 幂等** —— 同一台机器重装客户端不该每次吃掉一个额度。

`[?]` **`device_key` 可伪造，改个值就能再建一台。** 要不要防、防到什么程度，是个决定。

`[i]` 我倾向**接受它是软的**：设备额度的目的是挡"一个账号全家/全宿舍用"，
而那类用户不会去逆向客户端。**真要防专业共享，靠的是并发 IP 检测，不是设备 ID**
—— 这也是 §3.5 倾向保留 `alive_ips` 作信号（选项 A）的原因。
绑硬件特征在 Android 上不可靠、在 Windows 上侵入性强，代价不划算。

## 4. 迁移（零中断）

```
① 建表
② 为每个现有用户建一条设备：
     name      = "默认设备"
     uuid      = users.uuid          ← 沿用，客户端无感
     passwd    = users.passwd        ← 沿用
     sub_token = users.invite_token  ← 沿用，老订阅链接继续可用
③ 部署：NodeUserService 开始按设备下发
④ users.uuid / users.passwd 保留为只读遗留字段，晚一个版本再清
```

`[!!]` **第 ② 步沿用现有值，是整个迁移不中断的原因。** 没有任何用户需要重新导入。

`[!]` 现在做最便宜：**0 个付费用户**，没有人的 uuid 已经嵌在客户端里。
晚一个月，成本是"全员重新导入订阅"。

## 5. 要改的地方（逐处）

| 处 | 改什么 | 风险 |
|---|---|---|
| `NodeUserService` | 按设备下发，`id` 用 `device.id` | 低（形状不变） |
| `TrafficService::record` | device → user 映射后再累加 | **中**：计费面，改错会记错账 |
| `SubController::show` | 先查设备 token，回退用户 token | **高**：用户唯一入口，改坏没人能连 |
| `SubscriptionService` | 6 处 `$user->uuid` → `$device->uuid` | 中 |
| `NodeSettingController` | 重置凭据 / 重置订阅改成按设备 | 低 |
| `user/devices.blade.php` | 从"在线 IP 列表"改成"我的设备" | 低 |
| 后台用户详情 | 显示设备列表 | 低 |
| 后台套餐编辑 | 新增 `device_limit` | 低 |

`[!]` `ForwardRuleService` 里的 uuid 是**中转→落地的规则凭据**，与用户凭据无关，**不动**。

## 6. 风险与未测

`[?]` **节点下发条数变成 用户数 × 设备数。** 1000 用户 × 4 设备 = 4000 条/次。
soga/xray 在这个量级应该没问题，但**本项目未测**。上线前要拿假数据实测一次
（既测面板生成耗时，也测节点内核 ApplyUsers 的耗时）。

`[?]` **mod_mu 的 `id` 语义会偏离真实 sspanel**（那边 `id` 是用户 id）。
我们自己控制两端，安全；但必须写进 `compatibility/`，
**别让后人以为还能直接对接原版 sspanel**。

`[!]` **`user_devices.uuid` 必须全局唯一**，不只是用户内唯一 ——
xray 的入站按 uuid 认人，撞了就是两个人共用一条身份。

## 7. 明确不做

- `[!]` **不做自动设备识别**（指纹、行为特征）。协议里没有这个信息，
  任何"识别"都是猜，而猜错的代价是误封用户。
- `[!]` **不在本次做按设备的流量统计**。技术上顺手（数据就在那），
  但它会引出"按设备限速""按设备封禁"一串需求，属于另一个决定。
  先只做归属，统计以后再说。
