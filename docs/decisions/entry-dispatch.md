# D-5 —— 入口分流在 DNS 层实现

> 承接 D-4（`relay-boundaries.md`）。D-4 保证了**发给客户端的是门牌而不是 IP**；
> D-5 回答**那个门牌能干什么**，以及**这件事为什么只能在 DNS 层做**。

---

## 决定

**同一个入口域名，对不同来源返回不同的 A 记录。分流规则配在 DNS 服务商，不在面板。**

```
entry.<另买的域名>
    ├─ 移动线路 → 中转 A 的 IP
    ├─ 电信线路 → 中转 B 的 IP
    ├─ 联通线路 → 中转 B 的 IP
    └─ 默认     → 中转 B 的 IP
```

面板侧**不需要任何改动**：`EntryDomain` 记录「哪个域名属于哪台中转」，
`Node::entryHost()` 照常发那一个域名。分流发生在域名解析的那一刻，面板看不见也不需要看见。

---

## 为什么只能在 DNS 层 —— 面板结构上做不到

`[!!]` **不是「DNS 更方便」，是面板在结构上没有这个信息。**

| 环节 | 能否知道用户此刻用哪个运营商 |
|---|---|
| 面板生成订阅 | **不能**。用户可能在 WiFi 上下载订阅，在 4G 上使用 |
| 订阅下发之后 | **不能**。订阅是静态文本，客户端不会回来重新问 |
| 客户端发起连接 | 能，但客户端不会把这个信息告诉面板 |
| **DNS 解析** | **能** —— 它发生在连接的那一刻，从用户当时的真实网络发起 |

再加一条：**同一个用户一天会换好几次网络**（家里电信、公司联通、外出移动）。
任何「下发时决定」的方案，第二次换网络就失效了。

因此分流只能是**解析期**行为，不能是**下发期**行为。

### 为什么不能给每个用户发不同的订阅

理论上可以按注册 IP 猜运营商，然后发不同订阅。三个问题：

1. 注册时的网络 ≠ 使用时的网络
2. 订阅内容因用户而异 → 无法缓存、无法比对、出问题时不可复现
3. `[!!]` **会破坏 D-4 的收益**：订阅稳定性的全部意义就是「用户手里那份长期不变」

---

## 与 D-4 的关系

D-4 说「对外发地址一律走 `entryHost()`」。**D-5 是那条规则的兑现理由之一。**

如果订阅里发的是裸 IP（D-4 曾经违反过一次），分流无从谈起 ——
一个 IP 不可能对不同运营商表现不同。**先有门牌，才谈得上门牌指向哪里。**

## 我们的收益（具体到已实测的数字）

`[D]` 已有两台机器的三网实测：

| | 电信 | 联通 | 移动 |
|---|---|---|---|
| DMIT `191.223.216.236` | 174 ms | 285 ms | **17 ms** |
| （待购中转 B，目标） | < 80 ms | < 80 ms | — |

**不分流**：只能二选一 —— 要么全走 DMIT（40% 用户 174–285ms），
要么全走 B（移动从 17ms 退化）。

**分流**：移动走 DMIT、电信联通走 B，**每个运营商都拿到自己那一路的最优**。

`[i]` DMIT 的移动 17ms 来自 CMI（`223.120.x` / AS58453）。
同期 SoCloud 的移动是 34ms，走普通联通 169。**这一路我们已经领先，不应该为了统一而放弃。**

## 现在缺的：没有任何东西会发现「入口挂了」

`[S]` 代码事实：

| | |
|---|---|
| `EntryDomainController::activate/block/rotate` | **全部人工** —— 管理员点按钮 |
| `rotate()` | **只登记，不改 DNS**。代码里明写「面板不会替你改」（`:85`） |
| `app/Console/`、`app/Jobs/` | 对 `EntryDomain` **零引用** |
| `EntryDomain::dnsStale()` | 只在 `admin/entry_domains/index.blade.php:60` 渲染时求值 |

`[!!]` **`dnsStale()` 不查 DNS。** 它比的是管理员手填的 `pointed_ip` 和 `node->server`，
即「登记的指向」对「节点真实 IP」。域名**实际解析到哪里**，面板从头到尾不知道。
名字容易让人以为它在做 DNS 探测 —— 它没有。

所以当前的恢复链路是：

```
用户投诉  →  你察觉  →  你判断是不是被墙  →  点 block  →  改 DNS  →  等 TTL
   ↑
几小时（瓶颈在这里，不在后面任何一步）
```

`[!]` 这与本项目已记录的同型问题一族：`Node::needsUsers()` 定义了零引用、
`LayerHealth::worst()` 只被自己的测试调用、`SubscriptionService` 直连落地发裸 IP。
**区别是这次不是「写了没接上」，是「状态机看起来会自动工作，实际只有人手在推」。**
三态 `active / standby / blocked` 的存在本身就容易让人以为它会自己转。

### 补法（未实施，按成本排序）

| 手段 | 能把「发现」压到 | 成本 |
|---|---|---|
| DNS 服务商自带的健康检查 / 故障切换 | 分钟级 | 含在付费套餐里 |
| 国内一台最便宜的机器定时 tcping 入口 | 分钟级 | 一台小鸡 + 一个 cron |
| 让 `dnsStale()` 真的去查 DNS | 只解决「登记漂移」，不解决「被墙」 | 小 |

`[!!]` **从香港/海外探测是无效的** —— GFW 拦的是国内出去的方向，
境外看这台机器一切正常。**探测点必须在国内。**

## 我们的实现（已落地）

`entry_domains` 加了一列 `cname_target`（`2026_09_16_210000` 迁移）：

```
EntryDomain.domain         门牌  —— 订阅发它（entryHost()），永不变
EntryDomain.cname_target   标签  —— 选填；A 记录挂在它上面
EntryDomain.pointed_ip     标签当前指向的 IP（人工登记）
```

| 方法 | 作用 |
|---|---|
| `dnsRecordHost()` | 该去改哪条 A 记录 —— 有标签发标签，没标签发门牌 |
| `isLayered()` | 是否启用了两层 |

三条行为，都有测试钉住（`tests/Feature/EntryDomainTest.php` 末尾）：

1. **提示指向标签** —— 指错了管理员会去动门牌的 A 记录，而门牌是 CNAME，动它整层就拆了
2. **标签不得等于门牌** —— `different:domain`，挡 CNAME 环
3. `[!!]` **轮换时同标签的兄弟一起同步 `pointed_ip`** —— DNS 上它们本来就一起变了；
   不同步，面板会亮出一批**假的**「该改 DNS」告警。
   只同步指向，**不动 status**：被墙的门牌不该因为别人轮换就自动复活。

### 分离性检查扩到了标签

`[!!]` `ServiceReadiness::entryDomainSeparation()` 现在同时检查 `domain` 和 `cname_target`。

**门牌换成了别的域名、标签还留在面板主域上 —— 等于没分离。**
封禁作用在**整个可注册域**上，整条 CNAME 链一起死，而那时你连后台都进不去。

三条注入反证跑过，全部变红，不是空真。

### 代价

冷缓存时多一次 DNS 往返。**换来的是换 IP 时永远不碰用户看得见的那个名字。**

---

## 边界

- **分流规则不进代码库。** 它在 DNS 服务商控制台，面板不读也不写。
  面板唯一的职责是记录「域名 ↔ 中转」的对应关系。
- **不因此修改 D-1 ~ D-4。** 那四条已封存。
- `[!]` **不要为了分流而给不同用户发不同订阅** —— 见上文「为什么不能」。

## 2026-09-20 复查 —— 用真实客户端 UA 重拉订阅

拿到了 SoCloud 订阅链接本人授权的一次直读（无状态 GET，不登录、不改任何数据；
凭据不入库不入文档）。结论推翻了本文两处，并补上了一直缺的那一环。

### `[!!]` 方法论教训：订阅要用真实客户端的 User-Agent 拉

`[D]` 同一条链接，UA 不同，发的模板不同：

| User-Agent | `nameserver-policy` | `ipv6: false` |
|---|---|---|
| `clash-verge/v1.6.0` | **有** | 无 |
| `ClashforWindows/0.19.23` | **有** | 无 |
| `Clash/1.18.0` | **有** | 无 |
| `Mozilla/5.0` | 无 | 有 |

**之前 09-15 / 09-17 那两份快照拿到的是「非 Clash」那一份**，于是得出了
「没有 nameserver-policy」的错误结论，还据此判定外部报告有误。

`[!]` 往后凡是拉第三方订阅做对照，**UA 必须伪装成真实客户端**，否则拿到的
不是用户实际拿到的那份。这个坑会静默地产生错误结论 —— 没有任何报错。

### 缺的那一环补上了：`nameserver-policy` 让权威服务器看见用户真实 IP

`[D]` Clash 系 UA 拿到的 `dns:` 段：

```yaml
dns:
  enable: true
  nameserver:
    - 114.114.114.114
    - 223.5.5.5
  nameserver-policy:
    'cp.paeadiy.com': '47.116.209.9:39053'
```

本文「未验证项」原本担心的是：

> 真实客户端问的是 114 / 223.5.5.5，权威服务器看到的是解析器的 IP，不是用户的，
> 分流是否准确取决于 EDNS Client Subnet。

**`nameserver-policy` 就是这个问题的解法**：把入口域名单独钉到自家 DNS 上，
强制客户端绕过公共解析器直接去问，于是那台服务器看到的是**用户的真实出口 IP**。

```
没有 policy   客户端 → 114(anycast) → 权威   权威只看见 114 的 IP，判不出运营商
有   policy   客户端 →          自家 DNS     看见用户真实 IP，可按运营商返回
```

`[?]` 仍未验证：**分流维度到底是不是"运营商"。** policy 保证了服务器能看见用户 IP，
但看见之后按什么维度分（运营商 / 地域 / 负载 / 套餐），没有证据。

`[?]` `47.116.209.9` 在 09-20 从本机查询 **:53 与 :39053 均超时**（09-15 时 :39053 可应答）。
下线、按来源过滤、还是链路问题，证据不足以判定。
`[!]` 如果它对国内真实用户也不应答，`nameserver-policy` 会让解析直接失败 —— 但我们
没有国内观测点可证，**不作结论**。

### `[!!]` 新发现：分流发生在 CNAME 层，不是 A 记录层

`[D]` 同一个名字，换解析器问，**返回的 CNAME 目标不同**：

| 解析器 | CNAME 目标 | A 记录 | CNAME TTL | A TTL |
|---|---|---|---|---|
| `223.5.5.5`（阿里） | `3x1.paeadiy.com` | `155.254.101.23` | **5** | 584 |
| `8.8.8.8`（Google） | `gy1.paeadiy.com` | `155.254.101.23` | **1** | 600 |

两个标签当前指向同一个 IP，**但标签本身是变量**。

这和我们实现的结构不同：

```
我们    门牌 ──CNAME──> 【一个固定标签】 ──A──> IP
        换 IP     改标签的 A 记录
        换线路    得去改门牌那条 CNAME(面板里改 cname_target)

他们    门牌 ──CNAME(按来源分流)──> 【多个标签,一条线路一个】 ──A──> 各自的 IP
        换 IP     改那个标签的 A
        换线路    改分流规则,不碰任何 A 记录
```

`[I]` **他们比我们多一个自由度**：把某个运营商从一条线路切到另一条，
只改 DNS 分流规则，不动任何 A 记录、也不动门牌。

`[!!]` **TTL 策略正好是反的，而且各自都对：**

```
他们   CNAME 1~5 秒(分流决定要新鲜) · A 600 秒(IP 本身稳定)
我们   CNAME 300 秒(没有分流,不需要新鲜) · A 60 秒(IP 就是会变的那个)
```

因为**各自"会变的东西"不在同一层**。我们没有分流层时，短 TTL 应该压在 A 上；
将来真要做运营商分流，短 TTL 要挪到 CNAME 上。

`[i]` 现在不改我们的实现 —— 单节点无分流，当前结构是对的。这条记下来，
等真的要做多线路分流时再回来看。

### 旁证：直连入口没有分流层

`[D]` `line.acetace.com` 直接是 A 记录，无 CNAME，TTL 60 → `203.175.14.49`
（09-15 观测到的是同 /24 的 `.45`）。

**直连不经中转，没有"选哪条线路"的问题，所以不需要分流层。** 结构上自洽。

### `[D]` 他们完全不做协议伪装

60 个节点的全量统计：

| 项 | 值 |
|---|---|
| 节点数 | 60 |
| 协议 | **60/60 vmess**，明文 TCP |
| `server` 字段 | 59 → `cp.paeadiy.com`；1 → `line.acetace.com`（名为「香港 \| V1 \| 直连」） |
| `tls` / `reality` / `servername` / `sni` | **0** |
| `network` / `ws-opts` / `grpc-opts` / `flow` | **0** |
| 端口范围 | 1032 ~ 52102，**区分落地的唯一手段** |

这把"端口区分落地"从 `[I]` 坐实为 `[D]`。

`[I]` **他们用线路质量替代了协议伪装**：入口在国内，用户到入口不过墙，
那一跳没有需要伪装的对象。我们在 `#101` 上做 REALITY 走的是另一条路 ——
不是谁对谁错，是**入口在境内还是境外**决定的。

`[?]` 国内入口的成本结构仍然没有证据（腾讯云 / EdgeOne / GAAP 几轮测算都算不起）。
**不要据此推断我们也该把入口放国内。**

### 顺带：全局段和我们几乎一字不差

`[D]` `mixed-port: 7897` · `external-controller: 127.0.0.1:39597` ·
`allow-lan: true`（**同样没有 `authentication`**）· 同一组 `nameserver`。

`[I]` 两边多半源自同一份流传很广的 Clash 模板。
`[!]` 所以 `allow-lan` 无认证**不是我们特有的问题**，但"别人也这样"不构成保留它的理由 ——
用户在公共 WiFi 下被蹭走的流量记在他自己账上。是否改，单独决定，不在本文范围。
