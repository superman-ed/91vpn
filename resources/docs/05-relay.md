# 05 · 中转架构

## 1. 形态

```
客户端 ──→ 中转（香港）──→ 落地（日本）──→ 互联网
           转发规则监听      节点自身端口
```

中转做的是 **L4 透传**：不解协议、不认证用户，原样把字节搬给下一跳。
用户的加密协议（vmess / vless+REALITY）在**落地**终结。

## 2. `[!!]` D-1：中转不碰用户

| | 中转 | 落地 |
|---|---|---|
| 认证用户 | 否 | 是 |
| 持有用户名单与凭据 | **否** | 是 |
| 上报按用户流量 | **否**（按规则上报） | 是 |
| 进用户订阅 | 否（订阅发的是它的**入口地址**） | 是 |

面板在**读写两个方向**都有守卫：`/mod_mu/users` 对中转返回空，
`/mod_mu/users/traffic` 与 `/users/aliveip` 对中转直接拒绝。

`[!!]` 写方向那条是计费面：一台被接管的中转若能替任意用户记流量，
可以把别人的额度刷爆，或给自己的账号免单。

## 3. 转发规则

后台 → 转发规则。一条规则 = 一个**入站**（在哪些中转上监听什么端口）
+ 若干**出站**（转给谁）。

| 概念 | 说明 |
|---|---|
| 入站类型 | `direct`（裸端口转发，不解协议）/ `vmess` / `vless` / `trojan` / `socks` |
| 入站节点集 | 这条规则要在哪几台中转上生效 |
| 监听端口 | 单个、范围（`30001-30010`）或逗号列表 |
| 出站 | 目标地址:端口，或目标节点集；分 `primary` / `backup` 两个池 |
| 均衡 | `roundrobin` / `random` / `leastping` … |
| 健康检查 | 间隔、连续失败/成功阈值 |

保存后**不是立刻生效**：节点要到下一个拉取周期才看到它。列表里的「节点同步」
一列显示它到没到。

## 4. `[!!]` PROXY protocol：真实客户端 IP

中转透传之后，落地看到的源 IP 是**中转的地址** —— 所有用户看起来都来自同一个 IP，
在线 IP 统计和审计就全废了。

解法是 PROXY protocol：中转在每条连接前面加一小段头，声明真实源地址。

**必须成对配置**：

| 中转出站 | 落地入站 | 结果 |
|---|---|---|
| `send_proxy_protocol = 2` | `accept_proxy_protocol = true` | ✅ 正确 |
| 发头 | 不收头 | ❌ 落地把头当成协议数据 → 连不上 |
| 不发头 | 收头 | ❌ 落地等一个永远不来的头 → 连不上 |

`[!!]` 配错的失败形态是**两端都不报错**：中转日志一切正常、落地一行都没有，
只有客户端知道连不上。面板的规则页是唯一能在出事**之前**发现它的地方 ——
保存规则时会做配对校验，并把结果标在规则列表上。

`[D]` v1 与 v2 不必匹配：收头端两个版本都认。

### 锁住落地端口

`[!!]` PROXY 头**无认证**。能连到落地那个端口的人，可以随意伪造客户端 IP，
污染 alive_ip 与审计记录。所以开了 `accept_proxy` 的落地**必须只对中转可达**。

一键部署会自动配防火墙（只放行中转源 IP）。手工配的话注意：

`[!!]` 机器归 ufw 管时**必须走 ufw**。往 INPUT 链尾追加一条 DROP 是**无效的** ——
ufw 的跳转排在前面，包在那里就被 ACCEPT 了，永远走不到链尾。
实测踩过：规则形状完全正确，端口照样对全世界开着。

## 5. `[!!]` UDP：两种情况完全不同

| 场景 | UDP |
|---|---|
| 用户流量（vless + vision 等）经中转 | **通** |
| 裸端口转发（`direct` 入站）+ `send_proxy_protocol` | **会被节点主动关掉** |

第一种通，是因为 vision 的 UDP 走 **XUDP 封装**，整条流包在那条 TCP 连接里，
中转从头到尾只看见 TCP。

第二种：`[D]` 实测 xray 会把 PROXY 头当成**一个独立的数据报**先发出去，
载荷在下一个包里 —— 接收端的整条 UDP 流**错位一个包**。而落地的
`acceptProxyProtocol` 是个 **TCP sockopt**，UDP 路径上没有它，
两端"正确配对"也剥不掉。

所以 agent 主动摘掉 UDP 并告警，面板在保存规则时提前提示。
**UDP 不通是能被发现的故障，静默错位不是。**

要在这条规则上承载 UDP，就关掉 `send_proxy_protocol`（代价是丢失真实客户端 IP）。

## 6. 订阅里给用户什么地址

`[!!]` 落地挂在中转后面时，客户端要连的是**中转 IP + 转发规则的监听端口**，
不是落地自己的地址 —— 落地那个端口往往还被防火墙锁成只收中转。

面板从转发规则**自动推导**：每条可达路径出一个订阅条目，
名字带入口后缀（如「日本01 · 香港中转」）。`accept_proxy` 的落地
不发直连条目（那种端口上直连必然被拒）。

`[!]` 不在节点上手填"对外地址"，是因为那份数据会和规则各自演化 ——
改了规则的监听端口而忘了回来改节点，订阅就静默失效。
