# D-6 —— 设备模型：一台设备一个凭据

状态：**设计待评审**（2026-09-23）
起因：L-08 —— 「在线设备数」量的其实是 IP 数

---

## 1. 问题

`[D]` 现状：设备上限靠 `alive_ips` 的 `(user_id, ip)` 去重来数，而它**两个方向都错**：

```
家里三台设备共用宽带出口   → 只算 1 台（少算，等于放过共享）
一台手机 Wi-Fi 切蜂窝      → 算 2 台（多算，等于误伤正常用户）
```

`[D]` 实测的套餐上限：轻量 3 · VIP① 4 · VIP② 7 · VIP③ 9 · 定制 36/60。
**轻量套餐用户开三台设备正好占满，一出门切网就超限。**

`[D]` 2026-09-23 已修掉「踢错人」那一半（`blockedIps()` 改按 `last_seen` 倒序），
但那只是把伤害从「踢掉你正在用的」降到「踢掉你确实不在用的」。**根本问题没动。**

---

## 2. 为什么只有一条路

`[S]` VLESS / VMess 的连接只携带 **UUID（标识用户）+ 源 IP**，**没有任何设备标识**。
客户端是标准的 Clash / Shadowrocket / sing-box —— 无法让它们多报一个字段。

`[!]` 考虑过并排除的：

| 方案 | 为什么不行 |
|---|---|
| 客户端上报设备号 | 要自研客户端。标准客户端做不到 |
| TLS 指纹 / 连接特征 | 不可靠；而且 REALITY 刻意把指纹归一化（`client-fingerprint: chrome`） |
| 继续按 IP 数，调参数 | 参数怎么调都改不了"IP ≠ 设备" |

**剩下唯一可行的：一台设备一个凭据 —— 凭据本身就是设备。**

---

## 3. 设计

### 3.1 表

```sql
user_devices
  id            bigint PK        -- 下发给节点的 id，流量按它回报
  user_id       bigint FK
  name          varchar(40)      -- 用户起的名字（"iPhone"、"家里电脑"）
  uuid          char(36) UNIQUE
  passwd        varchar(64)
  sub_token     char(32) UNIQUE  -- 每台设备一个订阅链接
  last_seen_at  timestamp NULL
  created_at / updated_at
```

`[!!]` **`id` 从 10,000,000 起自增**，与 `users.id` 刻意**不重叠**。
理由见 §3.2 —— 这不是洁癖，是让一种失败从"静默记错账"变成"明确拒收"。

### 3.2 节点下发与流量归属

```
下发   NodeUserService 每台【设备】一条：
         ['id' => device.id, 'uuid' => device.uuid, 'passwd' => device.passwd, …]
回报   节点把它收到的 id 原样报回来（[S] 现在就是这样，协议不用改）
归属   TrafficService 用 device.id 查 user_devices → 拿到 user_id → 累加到用户
```

`[!!]` **id 空间必须不重叠。** 半升级状态下，某个节点可能还缓存着旧的用户列表、
报回来的是 `users.id`。若两个空间重叠，那笔流量会被**静默记到另一个人头上**；
不重叠时它查不到设备、直接进"拒收"计数并告警 —— **失败要响，不要静默。**

`[!]` 用户级校验（`banned` / `class >= node_class`）位置不变，只是先经一次
device → user 的映射。

### 3.3 订阅

```
GET /sub/{token}
  ① 先查 user_devices.sub_token   → 用该设备的 uuid 生成
  ② 查不到再查 users.invite_token → 映射到该用户的【默认设备】（过渡期兼容）
```

`[!!]` ② 这条兼容是**迁移能做到零中断的关键**：老链接继续可用，老客户端继续能连。
上线后观察一段时间，确认没有流量再走 ② 时才删。

### 3.4 额度：从运行时惩罚改成配置时约束

```
现在   连接超限 → 踢人          永远会误伤，而且用户不知道为什么断
之后   添加设备超限 → 加不了     用户看到"你的套餐支持 4 台，已用 3 台"
```

`[!!]` 这是本设计**真正的收益**，比"数得准"更重要：
**把一个会误伤的运行时行为，换成一个说得清的配置时规则。**

`[!]` `plans` 新增 `device_limit`。**不复用 `ip_limit`** —— 两者语义不同，
复用会让"这个数字到底管什么"在迁移期无法解释。

### 3.5 `alive_ips` 怎么办

`[?]` **未决，需要你拍板。** 三个选项：

| | 做法 | 代价 |
|---|---|---|
| A | 保留上报、**不再踢人**，只作共享检测的信号 | 失去一个硬约束 |
| B | 改成**每设备**的 IP 上限（如 3） | 仍会误伤切网的用户，只是范围小了 |
| C | 整个移除 | 丢掉"一个凭据被 50 人共用"的唯一线索 |

`[i]` 我倾向 **A**：设备额度已经在配置时卡住了，运行时再踢一次是重复惩罚，
而它恰恰是误伤的来源。共享检测留着看，人工处理。

## 4. 迁移（零中断）

```
① 建表
② 为每个现有用户建一条设备：
     name      = "默认设备"
     uuid      = users.uuid          ← 沿用，客户端无感
     passwd    = users.passwd        ← 沿用
     sub_token = users.invite_token  ← 沿用，老订阅链接继续可用
③ 部署：NodeUserService 开始按设备下发
④ users.uuid / users.passwd 保留为只读遗留字段，晚一个版本再清
```

`[!!]` **第 ② 步沿用现有值，是整个迁移不中断的原因。** 没有任何用户需要重新导入。

`[!]` 现在做最便宜：**0 个付费用户**，没有人的 uuid 已经嵌在客户端里。
晚一个月，成本是"全员重新导入订阅"。

## 5. 要改的地方（逐处）

| 处 | 改什么 | 风险 |
|---|---|---|
| `NodeUserService` | 按设备下发，`id` 用 `device.id` | 低（形状不变） |
| `TrafficService::record` | device → user 映射后再累加 | **中**：计费面，改错会记错账 |
| `SubController::show` | 先查设备 token，回退用户 token | **高**：用户唯一入口，改坏没人能连 |
| `SubscriptionService` | 6 处 `$user->uuid` → `$device->uuid` | 中 |
| `NodeSettingController` | 重置凭据 / 重置订阅改成按设备 | 低 |
| `user/devices.blade.php` | 从"在线 IP 列表"改成"我的设备" | 低 |
| 后台用户详情 | 显示设备列表 | 低 |
| 后台套餐编辑 | 新增 `device_limit` | 低 |

`[!]` `ForwardRuleService` 里的 uuid 是**中转→落地的规则凭据**，与用户凭据无关，**不动**。

## 6. 风险与未测

`[?]` **节点下发条数变成 用户数 × 设备数。** 1000 用户 × 4 设备 = 4000 条/次。
soga/xray 在这个量级应该没问题，但**本项目未测**。上线前要拿假数据实测一次
（既测面板生成耗时，也测节点内核 ApplyUsers 的耗时）。

`[?]` **mod_mu 的 `id` 语义会偏离真实 sspanel**（那边 `id` 是用户 id）。
我们自己控制两端，安全；但必须写进 `compatibility/`，
**别让后人以为还能直接对接原版 sspanel**。

`[!]` **`user_devices.uuid` 必须全局唯一**，不只是用户内唯一 ——
xray 的入站按 uuid 认人，撞了就是两个人共用一条身份。

---

## 7. 明确不做

- `[!]` **不做自动设备识别**（指纹、行为特征）。协议里没有这个信息，
  任何"识别"都是猜，而猜错的代价是误封用户。
- `[!]` **不在本次做按设备的流量统计**。技术上顺手（数据就在那），
  但它会引出"按设备限速""按设备封禁"一串需求，属于另一个决定。
  先只做归属，统计以后再说。
