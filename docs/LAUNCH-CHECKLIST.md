## 一、必须在开放注册之前完成

> L-00 已修复，保留在此处是因为它的教训（断言要打在消费端）对下面几条同样适用。

### L-00 · 拿不到节点时的订阅 —— **已修复（2026-09-14）**

`[D]` 两个缺陷，用真 mihomo v1.19.14 实测确认，一次改掉：

**(1) 整份订阅根本加载不起来。** `Yaml::dump` 把空的 `proxies` 渲染成
`proxies: {  }`（空 map），而 Clash 要的是序列，mihomo 在**第 12 行直接 fatal**：

```
Parse config error: cannot unmarshal !!map into []map[string]interface{}
```

用户看到的只是「订阅导入失败」，查不到原因 ——
而这**正是**代码里「自动组必须整个去掉」那段注释要避免的后果：
那边小心翼翼保住了可加载性，最后一行的 `Yaml::dump` 又把它丢了。

**(2) 一旦 (1) 修好，`Proxy` 组回落到 `DIRECT` 就会生效。**
`[D]` 把 `proxies` 手工改成合法序列后跑真客户端：经代理的出口 IP
**等于**直连出口 IP（都是 `191.96.31.236`）—— 静默直连，用户以为在用代理、实际在裸奔。

这与本项目自己在 P0-2 立下的判据直接冲突。`lab/relay-failover-probe.sh` 的 `[D]`-4 原话：

> 关键不是"失败"，是【不能静默直连】。直连也能成功，那意味着用户以为在用代理、实际在裸奔。

那条管的是"两个中转都挂了"，这里是"一个节点都没有"，用户侧表现完全相同。

**修法**：`Yaml::DUMP_EMPTY_ARRAY_AS_SEQUENCE` + `Proxy` 回落到一个名为
`无可用节点（账号下没有节点，或节点全部离线）`、成员只有 `REJECT` 的组。
两者同时满足此前被当成一件事的两个要求：配置照样加载 ＋ 流量失败而不是直连，
而且组名本身就是解释。

`[D]` 修复后用面板的**真实输出**（不是手工改的副本）复验：
配置加载成功、经代理无输出、`/proxies/Proxy` 里读得到那个组名。
`[D]` 有节点的路径回归正常：自动组在、默认选中「自动选择」。

`[!!]` **这里我自己错过一次，值得记下来。**
最初的 P13 审计结论写的是「用户导入成功、客户端显示已连接、每个字节都没走代理」——
前半句是错的，因为我只读了生成的 YAML，**没有把它交给真客户端**。
实际用户根本导不进去。缺陷是真的、比原判断更严重（订阅完全不可用），
但我描述的用户症状是错的。
教训：订阅这类"产物给第三方消费"的东西，断言必须打在消费端，不能打在生成端。
`Yaml::parse()` 之后 `{  }` 和 `[]` 是同一个空数组 —— 本文件此前全部用例都走解析后的结构，
所以它们**全部**看不见这个缺陷。

### L-01 · `APP_ENV` 切回 `production`

`[D]` 当前是 `local`，这是**有意的**：防白嫖的收益在没有真实用户时为零，
而它挡住了唯一能测支付流程的手段（`mock-pay`）。

上线前必须切回 `production`，否则：

- `[D]` **任何登录用户可以对自己的待支付订单调 `/user/order/{id}/mock-pay` 免费拿到套餐**
  （实验 `tests/Feature/AuditU1MockPayTest.php` 已证明：订单 199 元一分没付，
  等级 0→5、配额 0→500GB、到期 +365 天）
- `[D]` 结账页会渲染一个人人可见的「模拟付款（开发）」按钮

改法：`.env` 一行 + 重启 `app`、`scheduler`（两者都是长驻进程，不重启不生效）。
`[!]` 判据以**运行时值**为准，不看 `.env` 文件。

### L-02 · epay 真实对接，并复核 `configured()` 的语义

`[D]` 三项设置（pid/url/key）都有值，`configured()` 返回 `true`，
但**对接尚未完成** —— `configured()` 只检查字段非空，不检查功能可用。

`[!!]` 这一点在审计中把我误导过一次：我据此判断"在线支付已可用，
所以关掉 mock 不影响正常功能"，而实际当时**没有任何可用的支付路径**。
对接完成前，不要把 `configured()=true` 读成"能收钱"。

### L-03 · 节点鉴权切到 `X-Node-Secret` 请求头

`[D]` agent 目前仍走 `?key=` 查询参数，后果：

- `[D]` 节点密钥**明文写进 nginx 访问日志**：取样 50,000 行中 **47,118 行**含 `key=<密钥>`
- `[D]` 该日志 → docker `json-file`，`LogConfig.Config` 为空 map，**无 `max-size`、不轮转**
- `[D]` 增速约 26,500 行/天
- `[S]` 持有节点密钥可调全部 14 个 mod_mu 接口，其中 `/mod_mu/users` 返回
  **全部用户的 `uuid` 与 `passwd`**（即代理凭据本身），
  `/mod_mu/nodes/{id}/info` 返回该节点的 **REALITY `private_key`**

`[?]` 当前需要本机读权限才能利用，**未证明存在远程读取路径**。
但上线后这条日志会持续留存真实用户的凭据入口。

顺带：给 docker 的日志驱动配 `max-size`/`max-file`。

## 二、上线前应当决定（不决定也能上，但要知道选了什么）

### L-04 · 已付费的流量包会凭空消失

`[D]` `applyDataPack()` 只 `increment` `transfer_enable`，不抬 `base_transfer_enable`；
而 `traffic:reset-monthly` 把 `transfer_enable` 设回 `base_transfer_enable`。
100GB 套餐 + 50GB 加油包，重置后剩 100GB。

`[D]` 存活时间取决于用户自己的 `next_reset_at`（用户看不到这个日期）：
实验里 500GB 的加油包两分钟后一点不剩。`deliver()` 是覆盖写，新买套餐同样会抹掉它。

`[S]` 结账页只写「立即叠加 XGB 到当前套餐」，没有任何有效期说明。

`[D]` 而且**没有任何记录**（L-09）：用户问「我买的 50GB 去哪了」，能拿出来的证据是零。

需要产品决定：(a) 加油包也抬高 `base_transfer_enable` (b) 单独计量、不受重置影响
(c) 保持现状但在结账页写清有效期。

### L-05 · 流量可能被重复计费

`[D]` agent 的上报是 **at-least-once**：投递返回错误就留在队首、下一轮重发。
这个选择本身是对的 —— xray 的计数器是 drain 语义（取走即清零），
数据一旦出了队列就没有第二个来源。

但它有一个没被写下来的前提：**面板得是幂等的**。而 `/mod_mu/users/traffic`
只是把字节数累加上去，没有批次 id、没有请求 id、没有去重表。

`[D]` 面板记完账但回程丢了（网关 502、客户端超时 —— 在 HTTP 上与真失败无法区分），
同一批就会被算两遍，用户被扣两次。`[?]` 频率未知，未做压测。

修法很小：`/mod_mu/users/traffic` 认一个批次 id，最近 N 分钟内见过就直接回 `ret:1`。

### L-06 · 管理员赠送套餐会**降级并缩减**用户权益

`[D]` 同场景对照（`tests/Feature/AuditP021GrantTest.php`）：
用户持 `class=9`、剩 99 天、1024GB，赠送一个 `class=3`/100GB 的套餐后：

| | class | 剩余天数 | 配额 |
|---|---|---|---|
| 起始 | 9 | 99 | 1024 GB |
| **正规购买**（同场景） | 9 | 99 | 1024 GB（进 `queued`，不动现有权益） |
| **管理员赠送** | **3** | 129 | **100 GB** |

`[D]` 时长是**延长**的（99→129），这一条没问题。
`[D]` 但**等级被降、配额被覆盖**，净效果是可用额度从 944GB 变成 100GB ——
与"补偿用户"的目的相反。
`[D]` 另外赠送**不扣库存**（限量套餐 5 → 赠送后仍 5，购买后 4）。

`[?]` 代码里没有任何说明表明这个场景被考虑过。**需要产品决定**期望行为：
(a) 和购买一样排队 (b) 立即生效但取两者较优 (c) 保持现状但在赠送页显示警告。

### L-07 · 弃单永远不会被自动关闭

`[D]` `ExpirePendingOrders` 的三态处理本身正确，但
`[D]` 网关对查不到的订单返回 `{"code":0,"msg":"查询订单失败"}`，
而 `EpayService::isPaidOnGateway()` 把 `code !== 1` 一律判为「不确定」→ 保守不关单。

`[D]` 当前 7 笔订单（8–14 天，合计 ¥1,485）就卡在这个循环里，
每 10 分钟重查一次，约 1,000 次/天的无效外呼，**只记 INFO，不进任何告警面**。

`[!!]` **这批订单的形态，正是将来每一笔弃单的形态** ——
用户创建订单但从未走到付款页，网关侧就没有记录。

`[?]` 修法需要网关文档才能定判据（区分"订单不存在"与"查询出错"），
而对接尚未完成。**与 L-02 一起处理。**

## 三、加固项（不阻塞上线）

### L-08 · 「在线设备数」量的其实是 IP 数

`[D]` 上报的键是 `(user_id, ip)`，而展示与限制用的名字是「设备」。两个方向都错：

- 家里三台设备共用宽带出口 → 只算 **1** 台
- 一台手机从 Wi-Fi 切到蜂窝 → 算 **2** 台

`[D]` 后者还会踢错人：`blockedIps()` 的「先到先得」按 `alive_ips.id` 升序保留，
而 `id` 是**第一次见到这个 IP** 时分配的 —— 于是保留了已经不在用的旧 IP，
踢掉的是用户此刻真正在用的那个。影响有界（旧 IP 掉出 120 秒窗口后自行恢复），
也就是每换一次 IP 最多被踢约两分钟。

`[D]` 信息其实是有的：两行的 `last_seen` 差了 60 秒，按 `last_seen` 倒序排就对了。

`[?]` 生产上有多少套餐真的设了 `ip_limit > 0` 未测（迁移默认 `0` = 不限）。

### L-09 · 系统自己改的东西，一条审计都不留

`[S]` 覆盖面做过机械核对：admin 下 57 条写路由，只有 `testGateway`（只读探测）没写审计。
也就是说**人点出来的**变更，记录是满的。

`[D]` 但定时任务改用户权益，一条不记：
`traffic:reset-monthly` 抹掉已付费的加油包、`orders:activate-due` 把等级从 0 改到 3、
`orders:expire-pending` 把订单改成 cancelled —— `AuditLog` 全是 0 行。
（含对照实验：同样的变更由人点出来，记录完整并带 `admin_id`。）

顺带：视图把 `admin_id=null` 渲染成「系统」，而 `null` 的另一个来源是**管理员被删**。
由于没有任何自动任务写审计，今天这个标签实际在说「操作人已经不在了」。

### L-10 · `activate()` 不复查订单状态

`[D]` `tests/Feature/AuditP025ActivateTest.php`：对同一订单调两次 `activate()`
→ **发两次货**（剩余天数 9 → 39 → 69）。
`[D]` 对照：同文件里的 `settleOrder` 连调两次，第二次被锁内复查拒绝 ——
**说明这不是框架限制，是少写了一层复查**。

`[D]` 但 `orders:activate-due` **顺序跑两次是安全的**（查询条件 `status=queued` 已不匹配），
`[?]` 只在两轮重叠、或与 `endCurrentPackage()` 并发时才可能触发。
`[S]` 调度未声明 `withoutOverlapping`。

改法很小：与 `settleOrder` 对齐（订单行锁 + 状态复查），或给调度加 `withoutOverlapping`。

### L-11 · 面板不可达时 fail-open 无时间上界

`[S]` agent 拉取用户失败即中止本轮，内核中的用户集**不动**；
`[S]` 未找到任何基于时长的降级逻辑。

`[I]` 后果：面板长时间不可达期间，被封禁/已过期/流量耗尽的用户**无限期继续可用**。

fail-open 对代理服务是合理默认，但**无上界**这一点代码里没有任何注释说明是选择过的。
上线前至少应当明确：这是有意的，还是没想过。

### L-12 · 充值返利只有单层幂等

`[S]` `rechargeRebate()` 自身**无幂等键**（`order_id` 恒为 null），
`[S]` `paybacks` 表**无唯一约束**。
`[S]` 幂等完全依赖调用方 `creditRecharge()` 的行锁 + 状态复查。

`[D]` 当前无可达的重复路径。但**任何新增的 `applyRecharge` 调用方只要忘了加锁就会重复返利**，
且不会有任何报错 —— 那两条模拟充值路径就是现成的例子。

### L-13 · 端口不在监听时，agent 知道，面板拿不到

`[S]` `xray.Core.Health()` 真的会去 dial 一次本地端口，所以这个状态 agent 检得出。
`[S]` 但 `status.NodeStatus` **没有 `Listening` 字段** —— agent 只写日志 + Prometheus，
心跳照常发，面板只看到一盏「在线」。

而同一个结构体为 `AcceptProxy` / `DestUp` 写下的理由逐字适用于这里：
「报它是因为失效是静默的……而看日志的前提是有人知道该去看」。

`[?]` 实际发生频率未知 —— 启动时 `waitListening` 会挡住，要成立须是启动成功**之后**退化。

`[!]` 好消息是另一半是对的：内核没起来时 `core.Traffic()` 失败、`push` 提前返回、
心跳跟着停，面板 180 秒后自动置离线。这条 fail-safe 已由
`TestNodeStatusStopsWhenCoreIsDown` 钉住（含反向对照）。

### L-14 · 存活统计分不清「节点活着」和「没人在看」

`[D]` 采样停 6 小时再恢复，`exposureSeconds()` 一秒不少地把 6 小时算进分母，
而 `observations` 只有 2（按 5 分钟一采本该 73）。

数据**足以**发现（`observations` 就在表里），但 `exposureSeconds()` 不看它，
`health:spells` 也不比对 —— 「6 小时无人观察」与「6 小时持续健康」在报表上完全相同。

node-days 是失效率的分母，调度停摆会让失效率被系统性低估。
而这台机器上已经发生过一次调度容器带陈旧 env 跑了 18 天。

### L-15 · 节点带宽统计漏记被拒收的流量

`[D]` 归属校验（banned / class 不够）在累加 `rawU/rawD` **之前** `continue`，
所以被拒的流量从用户账和节点账里**同时**消失：节点实际转发 27,000 字节，
`node_daily_traffic` 只记了 3,000。

字段注释写的是「原始上行(服务器真实带宽)」—— 与实际不符。
而且是静默的：负数记录会写 warning，归属不符的不写。

影响面：该字段喂着后台「今日流量/总流量」和每节点流量列，
也就是跟 VPS 账单对账时用的那个数。

### L-16 · 签到的非会员分支会吞掉并发的额度变更

`[D]` 防**重复签到**是对的（原子条件更新）。但非会员分支写的是**绝对值**
`min(读到的值 + 奖励, 封顶)`，于是读与写之间到账的加油包会被整个覆盖 ——
实验里 1GB + 10GB 加油包，签到后只剩 1GB 出头。

`[D]` 对照：会员分支用 `DB::raw("transfer_enable + 奖励")`，10GB 还在。
同一个方法的两个分支，并发安全性不同。

### L-17 · 在线 IP 上报不做归属校验

`[D]` 同一个节点、同一个被封用户：流量上报拒收，在线 IP 上报照单全收。
后果不是白嫖流量（那条堵住了），是审计与设备数记录可被污染。

`[!]` `mod_mu` 控制器里为**中转**专门写了这条理由，落地节点这边没走同一套。

### L-18 · `traffic_logs` 是死表

`[S]` 迁移建了表（带 `node_id`、`rate`、索引），代码里没有任何写入方。
后果：「这笔流量走的哪个节点」在系统里没有任何地方记录 ——
排查滥用、处理按节点的计费争议时没有依据。
