# 05 · 中转架构

**读之前**：不确定"落地""中转""PROXY protocol"是什么的话，
先过一遍 [00 · 术语表](00-glossary.md)，五分钟。

---

## 0. 什么时候需要中转

用户到落地的直连质量差时。典型场景：落地在日本，但用户直连日本绕路严重、
晚高峰丢包。在香港放一台中转，用户连香港、香港走优质线路到日本，整体更快更稳。

**代价**：多一台机器的钱、多一跳的延迟（通常远小于绕路省下的）、
以及配置复杂度——这一篇讲的就是这部分复杂度。

**不需要中转的情况**：直连质量本来就够好。别为了架构好看加中转。

---

## 1. 形态

```
客户端 ──→ 中转（香港）──→ 落地（日本）──→ 互联网
           转发规则监听      节点自身端口
```

中转做的是 **L4 透传**：不解协议、不认证用户，原样把字节搬给下一跳。
用户的加密协议（vmess / vless+REALITY）在**落地**终结。

"用户的流量在中转上是加密的、中转看不懂"——这既是安全性，也是下一节那条
硬边界的由来。

## 2. `[!!]` D-1：中转不碰用户

| | 中转 | 落地 |
|---|---|---|
| 认证用户 | 否 | 是 |
| 持有用户名单与凭据 | **否** | 是 |
| 上报按用户流量 | **否**（按规则上报） | 是 |
| 进用户订阅 | 否（订阅发的是它的**入口地址**） | 是 |

面板在**读写两个方向**都有守卫：`/mod_mu/users` 对中转返回空，
`/mod_mu/users/traffic` 与 `/users/aliveip` 对中转直接拒绝。

`[!!]` 写方向那条是计费面：一台被接管的中转若能替任意用户记流量，
可以把别人的额度刷爆，或给自己的账号免单。

## 3. 转发规则

后台 → 转发规则。一条规则 = 一个**入站**（在哪些中转上监听什么端口）
+ 若干**出站**（转给谁）。

| 概念 | 说明 |
|---|---|
| 入站类型 | `direct`（裸端口转发，不解协议）/ `vmess` / `vless` / `trojan` / `socks` |
| 入站节点集 | 这条规则要在哪几台中转上生效 |
| 监听端口 | 单个、范围（`30001-30010`）或逗号列表 |
| 出站 | 目标地址:端口，或目标节点集；分 `primary` / `backup` 两个池 |
| 均衡 | `roundrobin` / `random` / `leastping` … |
| 健康检查 | 间隔、连续失败/成功阈值 |

保存后**不是立刻生效**：节点要到下一个拉取周期才看到它。列表里的「节点同步」
一列显示它到没到。

## 3b. 手把手：加一台中转

假设你已经有一台跑着的落地（节点 ID 12，地址 `9.9.9.9:443`），现在要在香港
加一台中转。

### 第 1 步 · 在面板里建中转节点

节点管理 → 添加节点：

| 字段 | 填什么 |
|---|---|
| 名称 | `香港中转` |
| **角色** | **中转** |
| 地址 | 香港那台的公网 IP |
| **端口** | **0** |
| 协议 / 传输 | 随便（中转不解协议，这两项对它无意义） |
| 等级门槛 | `0` 即可 —— 中转本来就不进订阅（表单取值 0–9） |

`[!]` 端口填 0 是对的，不是漏填 —— 中转的监听端口来自转发规则。
面板会在列表里显示「端口见转发规则」。

`[!]` 等级门槛的表单取值是 **0–9**。想把某个节点藏起来不给用户看，
用**禁用**（`enabled = false`），不是用一个很大的等级 ——
禁用的节点照常拉配置、照常跑，只是不进订阅。

保存后记下它的 **节点 ID** 与 **secret**。

### 第 2 步 · 装中转上的 agent

和落地一样（见 [02 §8](02-quickstart.md)），只是节点 ID 换成中转那个。
装完它会去面板拉转发规则——现在还没有，所以它什么都不监听，这是正常的。

### 第 3 步 · 建一条转发规则

转发规则 → 新建：

| 字段 | 填什么 |
|---|---|
| 名称 | `香港→日本01` |
| 入站节点集 | 勾上「香港中转」 |
| 入站类型 | `direct`（裸端口转发，不解协议） |
| 监听端口 | `30001`（用户将要连的端口） |
| 出站目标 | 落地的地址端口 `9.9.9.9:443`，或直接选落地节点 |
| 发 PROXY 头 | `2`（想让落地看到真实客户端 IP 就开，见下一节） |

保存后**不会立刻生效**——中转要到下一个拉取周期（默认 60 秒）才看到它。
规则列表的「节点同步」一列会显示它到没到。

### 第 4 步 · 让落地收 PROXY 头

`[!!]` 上一步开了发头，这一步就**必须**做，否则用户连不上而两端都不报错。

落地节点编辑页 → 勾上 `accept_proxy_protocol` → 保存。
落地的 agent 下个周期会重启内核并开始收头。

### 第 5 步 · 锁住落地端口

`[!!]` 开了收头之后，**任何能连到落地那个端口的人都能伪造客户端 IP**。
必须只放行中转：

用面板的一键部署重装落地时会自动配（它知道该放行哪些中转 IP）。
手工的话见下一节的防火墙部分。

### 第 6 步 · 验证

`[!]` 本节六步**实际执行过一遍**（2026-09），下面写的是真实会看到的东西。

1. **面板规则列表**：不该有**红色**告警（`reject` / `broken` 那两档）。

   `[!!]` 但你多半会看到**两条橙色的 warn，它们是正常的**，别被吓到：

   | 看到的 | 是不是问题 |
   |---|---|
   | 「本规则不承载 UDP（出站发 PROXY 头，节点会关掉 UDP）」 | **正常** —— 开了发头就必然如此，见 §5 |
   | 「落地的上报已过期」 | **刚建完规则时正常** —— 配对校验要落地最近 5 分钟内的上报。等落地下一个心跳（默认 60 秒）就会消失；一直不消失才是问题 |
2. 用户订阅里应该出现一条「日本01 · 香港中转」，地址是**香港的 IP**、端口 `30001`
3. 用客户端连那一条，能出网即成功
4. 落地的在线 IP 里看到的应该是**用户的真实 IP**，不是香港中转的 IP
   —— 这条验证的是 PROXY protocol 真的生效了

### 出问题时

| 现象 | 查什么 |
|---|---|
| 订阅里没出现中转那条 | 规则启用了吗？中转节点在线吗？（离线的中转不进订阅） |
| 连不上，两端日志都正常 | **PROXY 头配对**——最常见的原因，看规则页的校验结果 |
| 校验报「这个地址上有多台落地节点」 | 一个 IP 上挂了多台落地（不同端口），而出站的**目标端口**没对上任何一台。把端口写成落地实际监听的那个 |
| 连得上但落地看到的 IP 是中转的 | 发头没开，或落地没收头 |
| 落地直连也能连上 | 落地端口没锁，见第 5 步 |

## 4. `[!!]` PROXY protocol：真实客户端 IP

中转透传之后，落地看到的源 IP 是**中转的地址** —— 所有用户看起来都来自同一个 IP，
在线 IP 统计和审计就全废了。

解法是 PROXY protocol：中转在每条连接前面加一小段头，声明真实源地址。

**必须成对配置**：

| 中转出站 | 落地入站 | 结果 |
|---|---|---|
| `send_proxy_protocol = 2` | `accept_proxy_protocol = true` | ✅ 正确 |
| 发头 | 不收头 | ❌ 落地把头当成协议数据 → 连不上 |
| 不发头 | 收头 | ❌ 落地等一个永远不来的头 → 连不上 |

`[!!]` 配错的失败形态是**两端都不报错**：中转日志一切正常、落地一行都没有，
只有客户端知道连不上。面板的规则页是唯一能在出事**之前**发现它的地方 ——
保存规则时会做配对校验，并把结果标在规则列表上。

`[D]` v1 与 v2 不必匹配：收头端两个版本都认。

### 锁住落地端口

`[!!]` PROXY 头**无认证**。能连到落地那个端口的人，可以随意伪造客户端 IP，
污染 alive_ip 与审计记录。所以开了 `accept_proxy` 的落地**必须只对中转可达**。

一键部署会自动配防火墙（只放行中转源 IP）。手工配的话注意：

`[!!]` 机器归 ufw 管时**必须走 ufw**。往 INPUT 链尾追加一条 DROP 是**无效的** ——
ufw 的跳转排在前面，包在那里就被 ACCEPT 了，永远走不到链尾。
实测踩过：规则形状完全正确，端口照样对全世界开着。

## 5. `[!!]` UDP：两种情况完全不同

| 场景 | UDP |
|---|---|
| 用户流量（vless + vision 等）经中转 | **通** |
| 裸端口转发（`direct` 入站）+ `send_proxy_protocol` | **会被节点主动关掉** |

第一种通，是因为 vision 的 UDP 走 **XUDP 封装**，整条流包在那条 TCP 连接里，
中转从头到尾只看见 TCP。

第二种：`[D]` 实测 xray 会把 PROXY 头当成**一个独立的数据报**先发出去，
载荷在下一个包里 —— 接收端的整条 UDP 流**错位一个包**。而落地的
`acceptProxyProtocol` 是个 **TCP sockopt**，UDP 路径上没有它，
两端"正确配对"也剥不掉。

所以 agent 主动摘掉 UDP 并告警，面板在保存规则时提前提示。
**UDP 不通是能被发现的故障，静默错位不是。**

要在这条规则上承载 UDP，就关掉 `send_proxy_protocol`（代价是丢失真实客户端 IP）。

## 6. 订阅里给用户什么地址

`[!!]` 落地挂在中转后面时，客户端要连的是**中转 IP + 转发规则的监听端口**，
不是落地自己的地址 —— 落地那个端口往往还被防火墙锁成只收中转。

面板从转发规则**自动推导**：每条可达路径出一个订阅条目，
名字带入口后缀（如「日本01 · 香港中转」）。`accept_proxy` 的落地
不发直连条目（那种端口上直连必然被拒）。

`[!]` 不在节点上手填"对外地址"，是因为那份数据会和规则各自演化 ——
改了规则的监听端口而忘了回来改节点，订阅就静默失效。
