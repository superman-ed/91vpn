## 一、必须在开放注册之前完成

> L-00 已修复，保留在此处是因为它的教训（断言要打在消费端）对下面几条同样适用。

### L-00 · 拿不到节点时的订阅 —— **已修复（2026-09-14）**

`[D]` 两个缺陷，用真 mihomo v1.19.14 实测确认，一次改掉：

**(1) 整份订阅根本加载不起来。** `Yaml::dump` 把空的 `proxies` 渲染成
`proxies: {  }`（空 map），而 Clash 要的是序列，mihomo 在**第 12 行直接 fatal**：

```
Parse config error: cannot unmarshal !!map into []map[string]interface{}
```

用户看到的只是「订阅导入失败」，查不到原因 ——
而这**正是**代码里「自动组必须整个去掉」那段注释要避免的后果：
那边小心翼翼保住了可加载性，最后一行的 `Yaml::dump` 又把它丢了。

**(2) 一旦 (1) 修好，`Proxy` 组回落到 `DIRECT` 就会生效。**
`[D]` 把 `proxies` 手工改成合法序列后跑真客户端：经代理的出口 IP
**等于**直连出口 IP（都是 `191.96.31.236`）—— 静默直连，用户以为在用代理、实际在裸奔。

这与本项目自己在 P0-2 立下的判据直接冲突。`lab/relay-failover-probe.sh` 的 `[D]`-4 原话：

> 关键不是"失败"，是【不能静默直连】。直连也能成功，那意味着用户以为在用代理、实际在裸奔。

那条管的是"两个中转都挂了"，这里是"一个节点都没有"，用户侧表现完全相同。

**修法**：`Yaml::DUMP_EMPTY_ARRAY_AS_SEQUENCE` + `Proxy` 回落到一个名为
`无可用节点（账号下没有节点，或节点全部离线）`、成员只有 `REJECT` 的组。
两者同时满足此前被当成一件事的两个要求：配置照样加载 ＋ 流量失败而不是直连，
而且组名本身就是解释。

`[D]` 修复后用面板的**真实输出**（不是手工改的副本）复验：
配置加载成功、经代理无输出、`/proxies/Proxy` 里读得到那个组名。
`[D]` 有节点的路径回归正常：自动组在、默认选中「自动选择」。

`[!!]` **这里我自己错过一次，值得记下来。**
最初的 P13 审计结论写的是「用户导入成功、客户端显示已连接、每个字节都没走代理」——
前半句是错的，因为我只读了生成的 YAML，**没有把它交给真客户端**。
实际用户根本导不进去。缺陷是真的、比原判断更严重（订阅完全不可用），
但我描述的用户症状是错的。
教训：订阅这类"产物给第三方消费"的东西，断言必须打在消费端，不能打在生成端。
`Yaml::parse()` 之后 `{  }` 和 `[]` 是同一个空数组 —— 本文件此前全部用例都走解析后的结构，
所以它们**全部**看不见这个缺陷。

### L-03 · 节点鉴权切到 `X-Node-Secret` 请求头 —— **代码已就绪，待逐台部署**

原状：agent 走 `?key=`，于是密钥被逐条记进访问日志。
`[D]` 取样 50,000 行中 **47,118 行**含明文密钥，增速约 26,500 行/天；
`[S]` 持有它可调全部 14 个 mod_mu 接口，其中 `/mod_mu/users` 返回
**该节点全部用户的 `uuid` 与 `passwd`**（即代理凭据本身），
`/mod_mu/nodes/{id}/info` 返回 REALITY `private_key`。

**已做（2026-09-14），两层：**

**① agent 可以改走请求头。** 新配置项 `webapi_auth`：

```ini
webapi_auth=header      # 密钥走 X-Node-Secret，URL 上不带
                        # 不写则默认 query，行为与以前完全一致
```

`[!!]` 默认**必须**留在 `query`：真实 sspanel-uim 只认 `?key=`，
改默认会让那些部署在升级 agent 的那一刻**集体掉线**，而且是静默的 ——
要等下一轮心跳才暴露。`node_id` 仍留在 query（它不是秘密，有的端点靠它定位节点）。

**② nginx 侧兜底遮蔽。** 面板已经先支持了请求头，但 agent 要逐台升级；
在那之前、以及任何别的客户端仍用 `?key=` 时，日志这一侧先堵住：

```nginx
map $request_uri $safe_uri {
    "~^(?<qpath>[^?]*)\?(?:.*&)?key="  "${qpath}?key=REDACTED";
    default                             $request_uri;
}
```

`[D]` 线上实测：重载后 20 秒窗口内 6/6 条真实 agent 请求全部记成 `key=REDACTED`，零明文；
`?flag=clash` 这类无害参数保留。

`[!]` 两个踩过的坑写在配置注释里：
最初正则写成 `\?.*(^|&|\?)key=`，要求 `key=` 前有分隔符 ——
而 `key` 是**第一个参数**时那个 `?` 已被吃掉，恰恰最常见的 `?key=…` 匹配不上；
标记最初用中文，nginx 会把非 ASCII 逐字节转义成 `\xE5\x90\xAB…`，认得出但 **grep 不到**，也就没法拿它做告警。

**③ docker 日志轮转**（`docker-compose.yml` 的 `web` 服务加了 `max-size: 50m` / `max-file: 5`）。
`[!]` 需要**重建容器**才生效（`docker compose up -d web`），光 `restart` 不行 —— `LogConfig` 是创建时定的。

---

**剩下的是运维动作，需要你来做：**

1. **逐台给 agent 加 `webapi_auth=header` 并重启** —— 这才真正让密钥不再上路
2. **轮换节点密钥**。已经写进历史日志的那些密钥，遮蔽是追不回来的；
   后台有 `node.regenerate_secret` 动作。换完要同步更新节点上的 agent 配置
3. **清掉历史日志**。当前 docker json-file 里还留着大量明文；
   `docker compose up -d web` 重建容器会顺带丢弃旧日志（重建即换新 log 文件）

### L-19 · 订阅仍在发节点裸 IP —— 入口域名池是空的

`[D]` 2026-09-17 查库：`entry_domains` **零条记录**，所以 `Node::entryHost()`
全部回退到 `server`，订阅里发出去的是中转的公网 IP。

后果：**IP 被墙时只能改节点配置 + 重发订阅 + 等客户端更新（默认 24 小时）**，
而用户在这 24 小时里是断的。D-4 里写过「买到第一台 Relay 后**立刻**登记入口域名」，
还没做。

`[!!]` **越晚做，代价越大。** 现在 0 个真实用户，切换成本为零；
等有 50 个付费用户再从裸 IP 切成域名，那是一次全员断线事件。
所以它排在 epay 前面 —— 不是因为更紧急，是因为**现在做免费**。

改法（后台 → 节点与网络 → 入口域名，`[!]` 面板只登记不代改 DNS）：

```
CNAME  entry.<另一个可注册域>  →  hk1.<同域>     TTL 600
A      hk1.<同域>              →  <中转当前 IP>  TTL 60
```

- `[!]` 可注册域必须 ≠ `app.91app.shop` —— `ServiceReadiness::entryDomainSeparation()`
  会报红，判据取最后两段（见 D-4）
- 用 CNAME 两层（D-5）：以后换机器只改 `hk1` 那条 A 记录，门牌一辈子不动
- 新增后是「备用」，**要手动点「设为在用」**，订阅才会发它
- 验收：`dig +short entry.<域>` 出 CNAME 再出 IP；然后拉一次订阅确认发的是域名

### L-21 · 套餐限速高于入口带宽

`[D]` 2026-09-17 查库的限速梯子：

```
轻量套餐 / VIP①   100 Mbps
VIP②              200 Mbps
VIP③ / 定制套餐    300 Mbps
```

`[!!]` **一个 VIP③ 用户就能吃掉整台 200Mbps 的入口。**

对照 `[D]`：SoCloud 试用层 **20Mbps**（明写在节点名里：「限 20 Mbs」），

入口 200Mbps 时建议 VIP③ 100 / VIP② 60 / VIP① 30 / 轻量 20。
`[i]` 100Mbps 的 VIP③ 仍是 SoCloud 的 2 倍，同时保证 2 人满速并发、20 人正常用不塌。

`[!]` **现在改零成本**（226 个账号全是 mock）；有付费用户之后再降限速，
那是一次产品降级事件。

`[!]` 另有一个缺口：`NodeUserService.php:61` —— 免费节点 + 非会员用**节点**的限速，
而三个节点全是「不限」。**免费用户目前不限速**，一个白嫖的就能占满入口。

## 二、上线前应当决定（不决定也能上，但要知道选了什么）

### L-04 · 流量包的清零规则 —— **告知已补（2026-09-14）**

`[!]` **行为本身是对的，不要改。** owner 已确认这是有意设计，对用户的口径是：

> 购买的流量包将会在您的会员到期日或流量重置日自动清零，请根据您的实际使用流量选择合适的流量包。

`[!!]` 这一条我**先报错过一次**（原标题是「已付费的流量包会凭空消失」）。
从代码看它非常像缺陷，而且历史也在误导：`2026_08_24_100008` 曾建过
`users.pack_transfer` 列，注释写「跨月保留、随套餐结束作废」——
**相邻的 100009 又把它删了**，理由是「加油包改为重置日/到期日清零」。后者才是现行意图。
任何人重新审这段代码都会得出同样的误判，所以把结论写在这里。

**不要做的事**：恢复 `pack_transfer`；或让 `applyDataPack` 同时抬高
`base_transfer_enable`（那会让会员**每月白拿一份**，从少给变成多给）。

**已做（2026-09-14）**：那句话已放进结账页的订单卡片，紧跟在「流量」那一行后面。
`[D]` `tests/Feature/AuditL04PackTest.php` 逐字钉住这句口径，
并有反向对照确认**普通套餐不显示它**（它只对流量包成立）。
原本钉住缺陷的几条断言已反转为规格守卫。

`[D]` 为什么这条值得在上线前做完 —— 实测的真实使用路径：

| | 用户看到的剩余 |
|---|---|
| ① 月初，100GB 套餐 | 100.0 GB |
| ② 用光了，还剩 5 天 | 0.0 GB |
| ③ 花 20 元买 50GB 加油包 | 50.0 GB |
| ④ 这 5 天用掉其中 10GB | 40.0 GB |
| ⑤ 月度重置 | **100.0 GB** |

他付了 50GB 的钱，实际只用到 10GB。而屏幕上的数字是 40 **涨到** 100 ——
**当时不会察觉**，所以不会立刻来问；年付会员一年经历 12 次。
加油包的购买时机又天然在周期尾部（用完了才买），剩余寿命系统性偏短。
一句话的告知能把这整类争议挡在购买之前。

`[D]` 会员到期那一半**已经正确**：`assertUsable()` 对非会员取
`min(transfer_enable, 免费封顶)`，所以到期后加油包自然失效
（字段里仍写着 150GB，但实际可用上限是免费封顶 2GB）。

### L-05 · 流量可能被重复计费

`[D]` agent 的上报是 **at-least-once**：投递返回错误就留在队首、下一轮重发。
这个选择本身是对的 —— xray 的计数器是 drain 语义（取走即清零），
数据一旦出了队列就没有第二个来源。

但它有一个没被写下来的前提：**面板得是幂等的**。而 `/mod_mu/users/traffic`
只是把字节数累加上去，没有批次 id、没有请求 id、没有去重表。

`[D]` 面板记完账但回程丢了（网关 502、客户端超时 —— 在 HTTP 上与真失败无法区分），
同一批就会被算两遍，用户被扣两次。`[?]` 频率未知，未做压测。

修法很小：`/mod_mu/users/traffic` 认一个批次 id，最近 N 分钟内见过就直接回 `ret:1`。

### L-06 · 后台「开通」—— **已定性：不修（2026-09-14）**

`[!]` 先纠正措辞：这个功能在产品里叫**开通**，不叫"赠送"。
入口是 `/admin/users` 每行的绿色「开通」按钮（`UserController@grant` / `@doGrant`）。
本条此前写成"赠送"，导致 owner 对不上号 —— 是记录的问题，不是功能不存在。

**owner 确认：这个按钮是自己测试用的，日常运营不使用。**

于是原来那条"会把用户降级"的担心**不成立**：
按「开一个套餐」的语义，`deliver()` 的覆盖写就是对的。
（实测过的那个场景 —— `class=9`/1024GB 的用户被开通 `class=3`/100GB 后降级 ——
只在"拿它给老用户补时长"时才是问题，而那不是它的用途。）

**不要做的事**：把 `doGrant` 改成排队、或改成"取两者较优"。
那会让它在真正的用途（把某个用户设成某个套餐）下反而不听话。

**已做（由这条引出）**：既然它会在**生产后台**上被用来测试，
就不能让测试数据混进经营数字。首页「已支付订单」原本按
`status IN (paid, queued)` 计数，不分 `pay_method` ——
`amount=0` 所以「累计收入」本来就对，被撑大的是**单数**。
现已排除 `pay_method = 'admin'`（收入、趋势图同口径）。

`[!!]` 实现上有个坑值得记：**不能**写成 `where('pay_method', '!=', 'admin')` ——
SQL 里 `NULL != 'admin'` 求值为 `NULL` 而不是 `true`，
那样会把 `pay_method` 为空的历史订单**一起排除**，单数反而变小。
`tests/Feature/AdminGrantNotCountedTest.php` 有一条专门守这个，
并已验证过它不是空真（换成错误写法立刻变红）。

`[?]` 仍未处理：开通**不扣限量套餐的库存**
（`decrement('stock')` 在 `completeOrder` 里，这条路绕过了）。
按"自用测试"的定位，影响很小；真要用于对外发放时再补。

### L-07 · 弃单永远不会被自动关闭

`[D]` `ExpirePendingOrders` 的三态处理本身正确，但
`[D]` 网关对查不到的订单返回 `{"code":0,"msg":"查询订单失败"}`，

`[!!]` **这批订单的形态，正是将来每一笔弃单的形态** ——
用户创建订单但从未走到付款页，网关侧就没有记录。

`[?]` 修法需要网关文档才能定判据（区分"订单不存在"与"查询出错"），

## 三、加固项（不阻塞上线）

### L-08 · 「在线设备数」量的其实是 IP 数

`[D]` 上报的键是 `(user_id, ip)`，而展示与限制用的名字是「设备」。两个方向都错：

- 家里三台设备共用宽带出口 → 只算 **1** 台
- 一台手机从 Wi-Fi 切到蜂窝 → 算 **2** 台

`[D]` 后者还会踢错人：`blockedIps()` 的「先到先得」按 `alive_ips.id` 升序保留，
而 `id` 是**第一次见到这个 IP** 时分配的 —— 于是保留了已经不在用的旧 IP，
踢掉的是用户此刻真正在用的那个。影响有界（旧 IP 掉出 120 秒窗口后自行恢复），
也就是每换一次 IP 最多被踢约两分钟。

`[D]` 信息其实是有的：两行的 `last_seen` 差了 60 秒，按 `last_seen` 倒序排就对了。

`[?]` 生产上有多少套餐真的设了 `ip_limit > 0` 未测（迁移默认 `0` = 不限）。

### L-09 · 定时任务的留痕 —— **已补（2026-09-14）**

`[S]` 人工操作原本就是满的：admin 下 57 条写路由，只有 `testGateway`（只读探测）没写。
缺的是**定时任务改用户权益时一条不记**。现已补上五个动作：

| 动作 | 何时写 |
|---|---|
| `user.traffic_reset` | 月度重置**确实清掉了流量包**时（配额变小） |
| `order.auto_activate` | 排队订单到期自动发货（记等级、到期日怎么变的） |
| `order.auto_cancel` | 超时未支付自动关单 |
| `order.reconciled` | 对账发现网关已付款、自动补发货 |
| `recharge.reconciled` | 充值单对账补到账 |

`[D]` 现在按用户搜得到：
「`xxx@x` 流量重置：配额 150.00 GB → 100.00 GB，其中流量包 50.00 GB 按规则清零
（重置前剩余 40.00 GB，已用 110.00 GB 归零）」——**答得上"抹掉了多少"**。

**口径（这部分比代码更容易错）：**

- **只在确实拿走了东西时记。** 免费用户那一支、以及没买过流量包的会员，
  重置只是把已用清零（等于把额度还给用户），不记 —— 否则每月每人一行，
  人工操作会被淹没，而人只会翻最上面那一屏。
- **`nodes:mark-offline` 刻意不记。** 它每分钟跑一次、节点抖动会反复翻转；
  节点上下线已由 `node_health_spells` 按存活区段完整记录。
  审计日志记的是**会变成争议的业务状态**，不是运维遥测。
- **动作沿用 `user.` / `order.` 前缀**，不另起 `system.` 组 ——
  这样按"用户"或"订单"筛时，人工与自动排在**同一条时间线**上。出事要看的就是这条线。
- 人工/自动的区分交给页面的 `?src=` 按钮（全部 / 人工操作 / 定时任务）。

**顺带修掉的一个假信息**：页面此前把 `admin_id=null` 一律显示成「系统」，
而当时根本没有自动任务写审计 —— 那个标签实际在说的是「管理员被删了」，字面意思却相反。
现在两者分开显示，且判据是**动作名**而不是 `admin_id` 是否为空。

`[!]` 三条机械校验挡住回归：未登记的动作 `system_audit()` 直接抛错（同 `AdminAccess::capFor`）；
每个命令用到的动作必须在 `SYSTEM_ACTIONS` 里；每个动作前缀必须有对应的筛选分组
（否则按分组筛时它们看不见）。

### L-10 · `activate()` 不复查订单状态 —— **已修（2026-09-14）**

`[D]` 缺陷是真的，且在**真并发**下可达。`tools/l10/run.sh`（两个独立进程同时激活同一笔订单）：

| 实现 | 进程 A | 进程 B | 用户剩余天数 |
|---|---|---|---|
| 修复前 | delivered | delivered | **69**（起点 9 + 30 + 30） |
| 修复后 | skipped | delivered | **39**（起点 9 + 30） |

**修复**：`activate()` 锁订单并在锁内复查状态，与同一个类里的 `settleOrder()` 对齐 ——
它一直是这个套路，所以这不是框架限制，是少写了一层。
返回值改为 `bool`；命令侧只有**真发了货**才计数、才写审计
（跳过时记一条"自动发货"是假记录，比不记更糟）。

`[!]` 加锁顺序定为**订单 → 用户**，与 `settleOrder()` 一致 —— 两处不一致会在并发时互相等成死锁。

**第二层**：调度侧给 `orders:activate-due`、`payment:reconcile`、`orders:expire-pending`、
`traffic:reset-monthly` 加了 `withoutOverlapping`（带分钟超时，避免进程被 kill 后锁永不释放）。
`[!!]` 这是兜底**不是修复本身** —— 它挡不住另一条路径：
用户点「立即结束当前套餐」也会调 `activate()`，那跟调度器不是同一个进程，调度侧的锁管不到。

`[!]` 顺序跑两次本来就安全（查询条件 `status=queued` 已不匹配），
所以单进程测不出这条缺陷。`AuditP025ActivateTest` 的断言已从"发两次货"反转为"第二次被挡掉"。

### L-11 · 面板不可达时 fail-open 无时间上界

`[D]` 消费端已验（`lab/failopen-probe.sh`，真 xray 客户端 → 我们的 agent → dest，四格全过）：

| | 场景 | 真客户端 |
|---|---|---|
| `[D]`-1 | 面板正常、用户在册 | 连得上（装置自检） |
| `[D]`-2 | 面板撤销该用户 | 连不上（撤销机制本身有效） |
| `[D]`-3 | 用户恢复后**面板挂掉** | 6 个拉取周期 / 48 秒内**始终可用** |
| `[D]`-4 | 面板回来且用户仍是撤销的 | 连不上 |

`[D]`-2 和 `[D]`-4 是必需的对照：没有它们，`[D]`-3 的"仍可用"可能只是撤销机制压根没接上。

`[!]` 48 秒证明不了「**无**上界」—— 那是结构性主张，观察多久都证不出来，
只能证**不存在任何可能触发降级的机制**。
`[S]` `TestNoTimeBasedUserExpiry` 做了这件事：配置面没有任何
stale/ttl/expire/grace/failopen 旋钮（有旋钮而默认关着，与根本没有这个概念，是两回事），
且连续 500 轮拉取失败后内核的用户集一次都不动（含"面板恢复即清空"的反向对照）。

后果：面板长时间不可达期间，被封禁 / 已过期 / 流量耗尽的用户**无限期继续可用**。

fail-open 对代理服务是合理默认，问题在于**无上界这件事代码里没有任何注释说明是选择过的**。
上线前至少应当明确：这是有意的，还是没想过。

### L-12 · 充值返利只有单层幂等

`[D]` 用**真并发**验过（`tools/l12/run.sh`：两个独立进程、各自的数据库连接）：

| | 入口 | 结果 |
|---|---|---|
| `[D]`-1 | `creditRecharge()`（行锁 + 状态复查） | 并发两次**只到账一次** ✅ |
| `[D]`-2 | `applyRecharge()`（一个忘了加锁的新调用方） | 并发两次**到账两次**：下线 200 元、邀请人双倍返利、`paybacks` 2 条 |

`[!!]` 必须是真并发。在单进程里连调两次测出来的是「顺序重放」，那是另一件事 ——
顺序重放会被状态复查挡住，而真并发考验的是行锁。混为一谈会得出"已经安全了"的错误结论。

`[S]` `rechargeRebate()` 自身无幂等键（`order_id` 恒为 `null`），`paybacks` 表无唯一约束。
幂等**完全**依赖调用方。现有调用方是对的；隐患是这条防线只有一层，
且新增调用方时没有任何东西会提醒你 —— 那两条模拟充值路径就是现成的例子。

### L-13 · 端口不在监听时，agent 知道，面板拿不到

### L-14 · 存活统计分不清「节点活着」和「没人在看」

`[D]` 采样停 6 小时再恢复，`exposureSeconds()` 一秒不少地把 6 小时算进分母，
而 `observations` 只有 2（按 5 分钟一采本该 73）。

数据**足以**发现（`observations` 就在表里），但 `exposureSeconds()` 不看它，
`health:spells` 也不比对 —— 「6 小时无人观察」与「6 小时持续健康」在报表上完全相同。

node-days 是失效率的分母，调度停摆会让失效率被系统性低估。
而这台机器上已经发生过一次调度容器带陈旧 env 跑了 18 天。

### L-15 · 节点带宽统计漏记被拒收的流量

`[D]` 归属校验（banned / class 不够）在累加 `rawU/rawD` **之前** `continue`，
所以被拒的流量从用户账和节点账里**同时**消失：节点实际转发 27,000 字节，
`node_daily_traffic` 只记了 3,000。

字段注释写的是「原始上行(服务器真实带宽)」—— 与实际不符。
而且是静默的：负数记录会写 warning，归属不符的不写。

影响面：该字段喂着后台「今日流量/总流量」和每节点流量列，
也就是跟 VPS 账单对账时用的那个数。

### L-16 · 签到的非会员分支会吞掉并发的额度变更

`[D]` 用**真并发**验过（`tools/l16/run.sh`：两个独立进程、各自的数据库连接、对表后同时发起）。
场景是「签到」和「加油包到账」撞在一起，起始配额 1GB、加油包 10GB、签到奖励 0.1–0.5GB：

| 分支 | 写法 | 最终配额 |
|---|---|---|
| **非会员** | `min(读到的值 + 奖励, 封顶)` — 绝对值 | **1.295 GB**（10GB 没了） |
| 会员（对照） | `DB::raw("transfer_enable + 奖励")` — SQL 自增 | 11.244 GB（都在） |

`[!!]` 必须是真并发。之前的 P21-B2 是在单进程里拿一个陈旧模型模拟交错 ——
那证明的是"如果读写之间隔了一次变更会怎样"，不是"这件事在真实并发下真的会发生"。

`[D]` 防**重复签到**本身是对的（原子条件更新，同日第二次 `affected=0`）。
注释也只论证了这一点 —— 它对的是「签到与签到」的并发，
漏掉的是「签到与其它额度变更」的并发。同一个方法的两个分支，安全性不同。

### L-17 · 在线 IP 上报不做归属校验

`[D]` 同一个节点、同一个被封用户：流量上报拒收，在线 IP 上报照单全收。

`[!]` `mod_mu` 控制器里为**中转**专门写了这条理由，落地节点这边没走同一套。

### L-18 · `traffic_logs` 是死表
