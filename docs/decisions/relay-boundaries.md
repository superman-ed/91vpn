## D-1 · 中转不认证用户

> 中转 / 跳板 / 入口一律不认证、不持有用户名单，只透传字节；**认证只在落地做**。
> —— `ModMu/UserController.php:18`

**读方向**：`/mod_mu/users` 不向 `role=relay` 的节点下发用户名单。

`[!!]` 这条判据曾经**定义了但从没被调用** —— `Node::needsUsers()` 存在、全项目零引用。
也就是说给节点标了 `role=relay`，照样把真实用户名单连同凭据发过去，
而**中转往往是租来的、最容易被接管的那一台**。
现象上还看不出异常：中转本来就不认证用户，多一份名单它也用不着。

**写方向**：中转上报的按用户流量、按用户在线 IP 一律不采纳。

- 流量：中转没有「这些字节属于谁」这个信息，它报的按用户流量只可能是伪造的。
  `[!!]` 这是**计费面** —— 一台被接管的中转若能替任意用户记流量，
  可以把别人的额度刷爆，或给自己的账号免单。中转的用量走**按规则**的上报。
- 在线 IP：中转没有用户身份，报上来的 `(user, ip)` 只能是编的。
  采纳它等于让被接管的中转能把任意用户挤下线、或污染审计记录。

**端点不返回 404 而返回空名单**：agent 在通用流程里会调它，
返回空是「我这里没有用户」的正确表达，让它拿 404 走错误路径是另一回事。

## D-2 · `inbound_cred` / `out_cred` 是节点间凭据，不是用户凭据

> 这是面板铸造的**节点间凭据**，不是用户凭据 —— 中转不认证用户（D-1）。
> —— `ForwardRuleService.php:139`

跨节点引用时，出站凭据 = 被引用规则的入站凭据，**编译期注入**（同文件 `:274`）。

因此这两者**允许**出现在 `compileForNode()` 的输出里。
把它们当成「用户凭据」而收紧，是对 D-2 的误读。

### 附带的既有约束

| | |
|---|---|
| **入站** REALITY `private_key` | **允许**。中转要伪装成 TLS 站点就必须终结 TLS，终结 TLS 就必须持有私钥。这是物理约束，不是设计缺陷 |
| **出站** REALITY `private_key` | **禁止**。拨号方只需 `public_key` / `short_id` / `server_names`。`ForwardRuleService` 在编译期主动 `unset`，防的是管理员误填 |

`[!]` 传输层参数（`ws` / `grpc` / `reality` 的 dest、server_names）**不能**塞进 `credential`：
那一列在 agent 侧是凭据（uuid/password/cipher/username），多出来的键要么被忽略、
要么被当成配置错误；语义上也不对 —— 它们不是秘密，混在一起会让「凭据轮换」
顺手把传输参数也换掉。

## D-3 · 节点配置的边界不变量（机械校验）

`compileForNode()` 的输出**不得**携带用户维度状态，**不得**携带出站 REALITY 私钥。

由 `tests/Feature/NodeConfigBoundaryTest.php` 机械保证，三个维度：

| 维度 | 判据 |
|---|---|
| **路径** | `private_key` 只允许匹配 `^rules\[\d+\]\.inbound\.reality\.private_key$` |
| **字段名** | 禁用名单从 `users` 表**实际列**推导（`Schema::getColumnListing`），不手写 —— 将来新增用户字段自动纳入 |
| **取值** | 取库里真实用户的 `uuid`/`passwd`/`email`/`api_token`/`invite_token`/`ref_code` 当靶子，逐个叶子比对 |

`[!!]` **第三个维度是关键。** `credential.uuid` 这个**键**是合法的，
但它的**值**绝不能是某个用户的 uuid。
只查键名会完全漏掉「把 User.uuid 赋给节点凭据」这类改动 ——
真正危险的不是 `key = uuid`，是 `node credential.uuid = USER.uuid`。
换句话说，测的是**数据的语义来源不得跨越 Node / User 边界**，
而不是粗暴禁止某个字段名。

同时有**正向断言**钉住允许项（`inbound_cred`、入站 REALITY 私钥、出站 `public_key`），
防止将来有人「顺手收紧」把它们一起禁掉。

### 反证

三类泄漏都注入验证过，测试必须变红：

```
不剥离出站私钥            → rules[0].outbounds[0].reality.private_key
用户 uuid 塞进节点间凭据   → rules[0].inbound.credential.uuid 的值等于 用户#1.uuid
transfer_enable 塞进规则   → 出现用户维度字段：rules[0].transfer_enable
```

另有一条测试钉住摊平函数本身，否则上面四条可能全是空真。

## D-4 · Client Entry Host ≠ Internal Dial Address

系统里有**两个不同的地址概念**，它们必须分开，不得统一：

| | 是什么 | 谁在用 |
|---|---|---|
| **Client Entry Host**<br>`Node::entryHost()` | 面向客户端的**门牌** | 订阅里发给用户的 `server` 字段 |
| **Internal Dial Address**<br>`Node::server` | 面板与节点之间、节点与节点之间**实际拨号**的地址 | `compileForNode()` 下发的 `dial`、面板侧探测、健康态匹配 |

`entryHost()` 的实现：有 `status=active` 的入口域名就发域名，否则回退发 `server`（向后兼容）。

### 为什么必须分开

**这不是某个函数的实现细节，是一条架构边界。** 下面这些能力全部依赖它：

```
多 Relay            一个门牌指向多台入口
DNS 切换            改 A 记录而非重发订阅
Relay 故障迁移       换机器时客户端无感
多地域入口           不同来源解析到不同入口
Landing Pool        出站池变化不影响客户端看到的门牌
健康检查            按 server 匹配 agent 上报的 dial
订阅稳定性          用户手里的订阅内容长期不变
```

### 统一了会怎样（两条后果，第二条是静默的）

1. **中转要多解析一次 DNS** —— 它已经知道落地的真实地址，绕经门牌毫无收益。
2. `[!!]` **健康态归因会全部失效，且不报错。**
   `SubscriptionService::hopKnownDead()` 用 `$landing->server.':'.$landing->port`
   去匹配 agent 上报的 `dial`。若下发的 `dial` 变成了门牌，匹配不上 ——
   而匹配不上的处理是「当作未知、一律保留入口」（那条规则本身是对的），
   于是**表现为一切正常，实际是这一层判断整个废掉了**。

由 `tests/Feature/EntryDomainCoverageTest.php` 最后一条钉住。

### 规则

- **凡是对外（客户端可见）发地址的代码路径 → 一律用 `entryHost()`**
- **凡是面板→节点、节点→节点的拨号 → 一律用 `server`**
- 新增「往订阅里写地址」的路径时，默认 `entryHost()`；要用 `server` 得说明理由

### 曾经违反过一次

`SubscriptionService::entrypoints()` 里有两处 `push`：

```php
$push($landing->server, ...);      // 直连落地 —— 发了裸 IP  ✗
$push($relay->entryHost(), ...);   // 经中转   —— 发了门牌  ✓
```

后果：直连落地的 IP 被墙时只能改节点 + 重发订阅 + 等客户端更新（默认 24 小时），
而用户在这 24 小时里是断的。

`[!]` 这与本项目另外两次同型问题一族 —— `Node::needsUsers()` 定义了零引用、
`LayerHealth::worst()` 只被自己的测试调用。**写了但没接上，现象上看不出异常。**
所以 D-4 配了机械校验，而不是只写一句约定。

### 入口域名必须与面板域名分属**不同的可注册域**

不是不同子域，是**不同的注册域名**。

`[!!]` 域名污染与封禁通常作用在**整个可注册域**上。
`entry.91app.shop` 和 `app.91app.shop` 是同一个 `91app.shop` ——
主域一旦被打，**面板和入口一起死**，而那时你连后台都进不去，没法改任何东西。

方向是双向的：

```
面板域名被关注  →  入口陪葬
入口域名被封    →  面板陪葬   ← 而入口被封是【常态、预期内】的事件
```

第二条更要命：入口域名被封是**routine**，你本来就准备好了换 A 记录；
但如果它和面板同域，一次例行的封锁就会把后台一起带走。

`[D]` SoCloud 就是分开的，而且分了**三个可注册域**：

| 域名 | 用途 |
|---|---|
| `doata.net` / `socloud.me` | 订阅与面板 —— 用户看得到、会分享、会出现在推广里 |
| `paeadiy.com` | 主入口 —— 只出现在订阅内容里 |
| `acetace.com` | 直连入口 |

我们查了一整轮，**从未在入口链路上见过它的面板域名**。

由 `ServiceReadiness::entryDomainSeparation()` 机械提醒（同域即报警）。

### 运维上的第一件事

买到第一台香港 Relay 后，**立刻**把它登记成入口域名的第一个 `active` entry，
**不要把它的公网 IP 直接写进用户订阅**。

`[!]` 那个入口域名要用**另外买的一个域名**，不要用 `xxx.91app.shop`（见上一节）。
一个域名几十块，买它去掉的是「面板与入口同生共死」这个单点 ——
比多买一台机器划算得多。

这样以后换机器、换供应商、增加第二台香港入口，都不需要重新设计订阅体系 ——
而如果第一天就把 IP 发了出去，那批订阅会一直带着它。
